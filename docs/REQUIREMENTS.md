# Requirements and technical choices

Status: requirements and mechanisms have been separated for the scope identified in this pass. The coordinated new technical design has independent global acceptance; [new architecture REVIEW](design/REVIEW.md) §7 records the fixed baseline and boundaries. This inventory covers the current target design and explicit additions in this round, without claiming a word-for-word audit of every historical discussion or completed product refactoring. Prior Typst reviews retain their fixed scopes and do not require inheriting old technology.

## 1. Design basis

Choose technology as for a new project, prioritizing confirmed user requirements. Sunk cost, existing code, document volume, protocol names and prior review acceptance create no obligation to inherit a mechanism. The user has selected Typst and native-first authoring; this is a current explicit constraint. Prefer official capabilities where native syntax can express the content, without adding another authoring language.

Distinguish what the user wants to accomplish, the reliability/privacy/experience conditions that the result must satisfy, and the proposed implementation. The first two define observable acceptance; the third can be replaced. Simplification must not delete required failure scenarios, or merely rename the old complexity.

Appearing in an old document or competitor survey does not automatically make something a requirement. An existing algorithm may be retained when current requirements justify it, based on suitability and verification.

## 3. History and compatibility

Retain historical inputs, reviews and experiments as traceable design evidence, not runtime dependencies. Old candidate CP, Notice, Proof, Policy, receipt and decoder versions must not enter the new implementation merely because they were documented. Earlier requirements to preserve protocol shapes or exact error ordering undergo technical reassessment rather than automatically constraining the new project.

Define compatibility requirements only for evidenced real data, deployed interfaces or user-confirmed compatibility targets. A repository prototype or unimplemented design does not establish that these exist. Preserve originals if real data is found, and explicitly scope import, conversion or compatibility. Do not delete user data or invent migration layers for undeployed candidates.

Translate the original 21 findings and subsequent findings into complete failure scenarios and user harm. Applicable problems must be solved by the new design, potentially using different mechanisms. Record why a scenario becomes inapplicable when its old mechanism is removed. Neither inherit the old fix mechanically nor transfer every historical CLOSED status to the new design.

## 4. Implementation basis

The coordinated design covers §5 requirements and §6 failure scenarios. [REVIEW](design/REVIEW.md) §7 records independent global design acceptance. Refactoring follows vertical slices in [INTEGRATION](design/INTEGRATION.md), connecting requirements, mechanisms and actual evidence. Documentation consolidation does not reopen the full design review; changes to scope or material contracts receive impact-based review.

Titles, subtitles, mixed headings, Word output, rich note types, five views and Chinese defaults remain in scope. Historical mechanisms are not compatibility obligations. Implementation, product acceptance and release are recorded separately.

### 5.2 Structured capabilities for all note types

On 2026-10-12 the user clarified that earlier simplification of people and other types addressed the inconvenience of expressing complex data with native AsciiDoc attributes. If Typst can implement the capabilities elegantly, that reason no longer justifies removing them; the same applies to other note types. This principle correction is U; concrete fields, interaction and mechanisms are D. It applies to people, organizations, tasks, projects, papers and all other built-in or custom types, not just people.

Earlier field reductions made for the old carrier have been superseded. Current [SOURCE](design/SOURCE.md) §§3–6 and the complete schema cover rich note-type capabilities. A simple common interface does not remove useful structures.

1. **Retain needs and reselect representations.** Cross-check historically selected business capabilities, especially fields or structures removed solely because the carrier was inconvenient; return those capabilities to design inputs. Multiple values, nested records, relations, employment/state history, important events and provenance may be retained where useful rather than uniformly flattened or relegated to body notes. Merely discussed candidates and explicitly deferred features remain separately recorded, without automatically adding everything to the first release.
2. **Separate native representation from application meaning.** Prefer native Typst values, arrays, dictionaries and applicable standard constructors, with centrally defined schema types and validation. Do not require embedded JSON merely to preserve old wrappers. Expressible nesting does not prove that queries, editing, relations, synchronization or permissions have been implemented.
3. **A simple interface does not require reduced data.** Common fields are easy to enter; optional information can be expanded in groups or added as repeated items. Unused complex capabilities require no input. Keep source understandable rather than demanding extensive internal metadata for an ordinary value. Each type's required fields follow its actual purpose; not every historical field becomes mandatory.
4. **Justify necessary mechanisms individually.** Design stable note references, relation directions, derived inverse views and historical records against their needs. Do not require manual maintenance of both directions, or remove useful relations merely because the old engine is removed. Per-value UUIDs, confidence, generic fact ledgers and old protocols are neither automatically restored nor prohibited in advance; if needed, identify the scenario and why a lighter solution is insufficient.
5. **Judge elegance across the complete workflow.** Check representative types across authored source, property forms, editing/undo, Query/views and import/export. References, sharing or history also require the corresponding identity, authorization and save/sync checks. Successful syntax compilation alone is insufficient. Record actual tradeoffs or unsupported capabilities explicitly rather than presenting old-language limits as product choices.

The rewrite must assign retention/redesign/deferral reasons and current owners to each capability class, covering historically selected capabilities without treating the entire old schema as the new implementation. At minimum, verify that equal contact values retain distinct labels/notes and order; employment and organization references preserve time and target meaning; ordered paper authors agree across forms, Query and export; task details remain body content with structured fields supporting views; and ordinary use does not require optional complex information. These are design checks, not executed product tests.

### 5.3 Library defaults and native style overrides

On 2026-10-12 the user confirmed library-wide default fonts, spacing, borders and other styles for body text, headings, lists, tables and other elements, with per-note and local overrides through native Typst. Ordinary use must not require handwritten style imports in every note. This outcome is U; style-file organization, compilation entry points, settings controls and dependency delivery are D.

Library defaults and note/local rules follow actual Typst scope and composition, without another style language or a fictitious universal precedence order. Settings controls and source editing use one style authority. Unrecognized custom rules remain intact with a source entry point; controls cannot overwrite or discard them. Style changes invalidate affected previews without editing individual author bytes, identities or original annotation ranges.

Personal dark mode, reading zoom and assistive display settings are distinct from document styles and do not alter source or export. Export distinguishes an exact original file from a reproducible style-dependency bundle. The latter includes the exact entry point, styles and deliverable fonts/resources, with explicit missing-dependency results. Verify library defaults, note/local overrides, style revisions and external opening; an application preview is not output verification.

### 5.4 Five views from source to reading

On 2026-10-12 the user reconfirmed five views. The middle three render headings and similar constructs while displaying syntax, reveal syntax on demand, and hide syntax completely while allowing UI edits. Five views are a U requirement; controls and mapping mechanisms are D. They cannot be reduced to three product modes named source, write and read.

| View | Required experience |
| --- | --- |
| V01 Source | Complete editable Typst source, with optional syntax highlighting; author markers remain visible. |
| V02 Rendered with syntax | Recognizable rendered styling for headings, emphasis and similar constructs while author syntax stays visible and editable; more than colored plain text. |
| V03 Syntax on demand | Normally show rendered content; reveal relevant source syntax when editing focus or an explicit action needs it. Other content stays rendered. Keyboard and touch can enter/leave without hover. |
| V04 Syntax-hidden UI editing | Hide Typst syntax in the document surface; edit through input, menus, toolbars and structural controls. Constructs without reliable controls or origin maps remain intact and explicitly read-only, with an explicit switch to another view; never silently reveal code or damage complex source. |
| V05 Read | Read-only body presentation without author syntax or body-editing controls; navigation, selection, copying and authorized independent annotations remain available. |

All five share one author source, current Draft and undo history, not five documents. Switching neither saves nor changes source and creates no content-undo entry. Preserve recoverable caret, selection and reading position; distinguish Draft preview from committed content. Paged versus continuous layout is separate; PDF preview cannot stand in for one of the five views. Syntax visibility grants no permissions.

Acceptance covers at least: the same heading/emphasis/link across all views; every author marker remaining visible in V02; keyboard/touch reveal and dismissal without lost input in V03; no syntax leakage and retained unsupported constructs in V04; no direct body editing in V05; transitions with unsaved Draft, selection, undo and IME; and invalid source or late projections never replacing newer input. These are requirements, not executed product tests.

### 5.5 Chinese support without per-note activation

On 2026-10-13 the user confirmed out-of-the-box Chinese in body text, titles, lists, tables, inline code, code blocks and text within equations, without a Chinese declaration, package import or font configuration in every note. This is a U clarification of RQ01–03, RQ20–21 and §5.3. Default font selection, delivery and language-setting implementation are D, not another author language.

Glyph display and language-aware layout/speech are separate obligations. Code language tags select syntax highlighting, not Chinese support. Text in equations uses native strings or text content, for example `$ "总价" = "单价" times "数量" $`. Quotes distinguish text from mathematical expressions; they are not a Chinese declaration, and the application must not silently rewrite valid math source.

Library defaults supply Chinese-capable fonts and language/region settings, with native note/local overrides. Body, code and math have separate font responsibilities. Missing glyphs in default Latin fonts must not produce tofu boxes, and Chinese text must not be repaired by replacing the entire math font. Basic scope includes simplified/traditional Chinese and mixed Chinese/Latin text. Rare characters outside declared coverage, author-disabled fallback or explicitly missing fonts preserve the original content and report the issue; no arbitrary font is promised to cover all Unicode.

Desktop, WebUI, Server/CLI compilation and offline intranets must not depend on incidental host Chinese fonts or public font CDNs. Preview, PDF, DOCX and standalone Typst projects validate their actual font/language delivery separately; editable output cannot replace Chinese text with paragraph images. The current [EDITOR](design/EDITOR.md) §8.6 owns the mechanism and CJK01–08 cases. These are design requirements, not executed product acceptance.
