# Requirements and technical choices

Status: current requirements include Folder Nodes, ordinary-file mode and Agent use cases. Independent acceptance of the earlier fixed technical baseline is retained; [REVIEW](design/REVIEW.md) §8 records current refinements. Requirement implementation, bounded probes and product acceptance remain separate.

## 1. Design basis

Choose technology as for a new project, prioritizing confirmed user requirements. Sunk cost, existing code, document volume, protocol names and prior review acceptance create no obligation to inherit a mechanism. The user has selected Typst and native-first authoring; this is a current explicit constraint. Prefer official capabilities where native syntax can express the content, without adding another authoring language.

Distinguish what the user wants to accomplish, the reliability/privacy/experience conditions that the result must satisfy, and the proposed implementation. The first two define observable acceptance; the third can be replaced. Simplification must not delete required failure scenarios, or merely rename the old complexity.

Appearing in an old document or competitor survey does not automatically make something a requirement. An existing algorithm may be retained when current requirements justify it, based on suitability and verification.

## 3. History and compatibility

Retain historical inputs, reviews and experiments as traceable design evidence, not runtime dependencies. Old candidate CP, Notice, Proof, Policy, receipt and decoder versions must not enter the new implementation merely because they were documented. Earlier requirements to preserve protocol shapes or exact error ordering undergo technical reassessment rather than automatically constraining the new project.

Define compatibility requirements only for evidenced real data, deployed interfaces or user-confirmed compatibility targets. A repository prototype or unimplemented design does not establish that these exist. Preserve originals if real data is found, and explicitly scope import, conversion or compatibility. Do not delete user data or invent migration layers for undeployed candidates.

Translate the original 21 findings and subsequent findings into complete failure scenarios and user harm. Applicable problems must be solved by the new design, potentially using different mechanisms. Record why a scenario becomes inapplicable when its old mechanism is removed. Neither inherit the old fix mechanically nor transfer every historical CLOSED status to the new design.

## 4. Implementation basis

The coordinated design covers §5 requirements and §6 failure scenarios. [REVIEW](design/REVIEW.md) §7 records independent global design acceptance. Refactoring follows vertical slices in [INTEGRATION](design/INTEGRATION.md), connecting requirements, mechanisms and actual evidence. Documentation consolidation does not reopen the full design review; changes to scope or material contracts receive impact-based review.

Titles, subtitles, mixed headings, Word output, rich note types, five views and Chinese defaults remain in scope. Historical mechanisms are not compatibility obligations. Implementation, product acceptance and release are recorded separately.

### 4.1 Scope alignment and delivery principles (2026-10-30)

Restore selected user capabilities reduced by AsciiDoc representation limits, without restoring wrappers, protocols or a universal fact system built only for that carrier. These are current scope decisions, not implementation or acceptance claims.

- **Core capabilities.** Keep ordinary writing, continuity across five views, rich native properties, queries, file organization, stable links and explicitly bounded Office exchange. Ordinary tasks must not require provenance, confidence, per-value identity or internal protocol details.
- **Rich capabilities used on demand.** Retain selected uses of employment and state history, multiple sources, disputed records, quantities and richer relations through optional fields, groups and templates. Ordinary notes must not require a complete HR, CRM or historical-research workflow. Optional use does not cancel promised editing, querying or export.
- **Explicit deferrals.** Full HR/CRM, unselected automatic relationship inference/writeback, a general fact-adjudication platform, complete project management and unselected connectors do not enter the first delivery merely because native values can express them. Retain existing inverse views and provenance-bearing derived relations; deferring automatic writeback does not remove them. Recording sources and disputes does not mean automatically deciding truth. New scope needs a user task and benefit; historical field counts are not completion goals.
- **Bound visual editing and format exchange.** Preserve complete legal Typst source and make common constructs usable. Explain local limitations and provide explicit source access for complex constructs that cannot be safely rewritten. Five views share author source, Draft and Undo, without promising reversible editing of arbitrary generated content. Verify Office semantics on actual supported hosts rather than promising lossless round trips for every document; retain originals, unknown information and precise loss reports.
- **Deliver by platform.** Windows daily use and installation may form an independently accepted delivery while other platforms follow according to actual capabilities. Retain every platform direction and open gate. One platform does not qualify the complete cross-platform version, and unfinished mobile work does not block separate delivery of an accepted Windows scope. Publication remains a separate action.
- **Measure performance by workload.** Separate ordinary writing, large source, complex layout and queries; record hardware, mode, cold/warm state, latency percentiles and the actual process-memory scope. Retain existing numbers as research targets rather than a simultaneous promise for every workload. Do not rename failed cases or relax existing checks to obtain a pass. Preview throttling, on-demand loading and explicit supported limits are permitted; preservation of accepted input and safe over-limit refusal cannot be weakened.

Reliable saves, retaining both conflict versions, revocation boundaries and original-request recovery are core outcomes that simplification cannot remove. Implement through existing SOURCE/EDITOR/FEATURES/CORE owners and ROADMAP cases, without another requirements or acceptance ledger.

#### 5.1.1 Hierarchical tags

Confirmed on 2026-10-20 as a v0.6.3 NAV03/NAV04 supplement between stage three and the 2D graph slice. Each tag has at most one parent in a shared forest with multiple roots. Parentage is adjustable organization governing browsing and explicit descendant filters, without type, property or permission inheritance. Parents remain directly assignable tags; no grouping-only tag type is added. One tag cannot occupy multiple parents. Assigning several tags to a note does not replace separately assessing a real future multi-parent requirement.

Notes record only directly assigned tags. For a note tagged only Rust in “Technology → Programming → Rust,” exact Programming does not match, while Programming and descendants does. Moving Rust out changes subsequent descendant-query results without writing ancestors into note source. Rename/reparent preserves tag identity, references and shortcut targets. Literal tags never become registered tags through equal names, slashes or hierarchical display.

The new tag-tree browser defaults to “this tag and descendants,” with a visible switch to “this tag only.” Existing exact conditions remain exact. Saving the current filter must preserve its explicit mode rather than reopening another scope from a tag alone. The first scope adds no implicit per-tag mode memory. Equal names remain valid; creation shows existing candidates, while assignment, parent selection and tree entries use segmented paths and sufficiently distinguishing ID suffixes. A slash in a name is literal; parent selection is separate, without automatic path parsing or case/Unicode-based merging.

The first scope includes creation under a selected parent, rename, reparent/to-root, tree browsing and descendant filters through the common Query, with equivalent keyboard entry points and existing cancellation/recovery. Tree read grants no additional note, field or Query rights; a complete tree does not establish complete note coverage. Creation, movement and querying close their authorization, sync, conflict and recovery obligations in this slice. Hard deletion, merge, multiple parents, ontology inheritance and manual ordering are deferred. Reversible hiding requires demonstrated cleanup needs and a separate decision, without reserved lifecycle state or implicit changes to matching/assignment. CORE §2.3 and FEATURES §§5.6,7.4 own the design; ROADMAP TAG01–10 owns completion gates. The contract now connects common Core/Query/UI/authorization and synchronization/Native consumers in the 0.6.3-rc.1 working tree, with whole-version acceptance still in progress. Alpha.3's flat tags describe the original candidate rather than establishing all new gates passed.

### 5.2 Structured capabilities for all note types

On 2026-10-12 the user clarified that earlier simplification of people and other types addressed the inconvenience of expressing complex data with native AsciiDoc attributes. If Typst can implement the capabilities elegantly, that reason no longer justifies removing them; the same applies to other note types. This principle correction is U; concrete fields, interaction and mechanisms are D. It applies to people, organizations, tasks, projects, papers and all other built-in or custom types, not just people.

Earlier field reductions made for the old carrier have been superseded. Current [SOURCE](design/SOURCE.md) §§3–6 and the complete schema cover rich note-type capabilities. A simple common interface does not remove useful structures.

1. **Retain needs and reselect representations.** Cross-check historically selected business capabilities, especially fields or structures removed solely because the carrier was inconvenient; return those capabilities to design inputs. Multiple values, nested records, relations, employment/state history, important events and provenance may be retained where useful rather than uniformly flattened or relegated to body notes. Merely discussed candidates and explicitly deferred features remain separately recorded, without automatically adding everything to the first release.
2. **Separate native representation from application meaning.** Prefer native Typst values, arrays, dictionaries and applicable standard constructors, with centrally defined schema types and validation. Do not require embedded JSON merely to preserve old wrappers. Expressible nesting does not prove that queries, editing, relations, synchronization or permissions have been implemented.
3. **A simple interface does not require reduced data.** Common fields are easy to enter; optional information can be expanded in groups or added as repeated items. Unused complex capabilities require no input. Keep source understandable rather than demanding extensive internal metadata for an ordinary value. Each type's required fields follow its actual purpose; not every historical field becomes mandatory.
4. **Justify necessary mechanisms individually.** Design stable note references, relation directions, derived inverse views and historical records against their needs. Do not require manual maintenance of both directions, or remove useful relations merely because the old engine is removed. Per-value UUIDs, confidence, generic fact ledgers and old protocols are neither automatically restored nor prohibited in advance; if needed, identify the scenario and why a lighter solution is insufficient.
5. **Judge elegance across the complete workflow.** Check representative types across authored source, property forms, editing/undo, Query/views and import/export. References, sharing or history also require the corresponding identity, authorization and save/sync checks. Successful syntax compilation alone is insufficient.
