# Typst Core: files, commits and operating boundaries

Status: **design-refinement-not-implemented**. Independent acceptance of the fixed earlier baseline remains historical; current refinements and evidence limits are recorded in [REVIEW](REVIEW.md) §8.

## 1. One file workspace and one author commit path

Weftext's native Rust Core serves Desktop, CLI, Server, WebUI and future Mobile. Local Desktop/CLI call local Core; their remote modes and WebUI call Server only. Offline hosted clients may retain Drafts but cannot grant themselves hosted commit eligibility. Mobile local writes require a qualified platform backend. Real-time collaboration remains later work; future OT/CRDT also submits an explicit author proposal.

Ordinary saves, field edits, creation, moves, copies, Trash, restoration, annotation suggestions, templates and business actions all use Core `Intent → Plan → OperationJournal → Receipt`. UI, converters, agents, synchronization and indexes have no second author write entry. Conversion and external execution use recoverable Jobs; a Job's workspace changes still enter the same Plan.

Persistent writes are ordered by actual conflict scopes. Multiple users may read, edit, retain Drafts and prepare concurrently. A physical replica's final durable commit coordinator may serialize briefly; this does not mean prolonged workspace-wide blocking or a single user. Different replicas may commit ordinary content offline without duplicating external execution responsibility.

## 2. Sole file and structure authority

A managed Node is `X/X.typ`. Its body, declaration, fields and author styling reside in that Typst source. SOURCE's explicit author roles define title and subtitle; no title is valid, and filename is only a display fallback. Resources are ordinary files; independent annotations use `weftext.annotations.json`. There is no second body or shared presentation database.

The exact root `.weftext-format` bytes are `weftext.typst.v1\n`. One `.weftext-workspace.json` records WorkspaceId, current schema and storage-contract selection. The marker selects a format; it grants no identity, permission or historical continuity. Directories without a valid contract are unmanaged, incompatible or incomplete as appropriate; no format guessing or automatic conversion occurs.

The directory tree is the only parent/name/path authority for live Nodes. Portable metadata does not maintain independently editable parent/children lists. A parent's sorting policy and a child's sparse manual rank record ordering that the tree does not express; natural name order is the default. The actual Trash directory tree defines its internal structure. A Trash record may retain the original location, batch and restoration membership because these are historical and restoration facts; they cannot override the live tree. An occupied restoration target conflicts rather than being overwritten.

`.weftext-rules` does not inherit `.gitignore`. One Core inventory separately records existence/visibility, Folder Node eligibility and explicit node-discovery boundaries. Ignored entries are hidden from ordinary lists and excluded from discovery, but remain backup bytes. Unmanaged entries remain visible, expandable and openable as ordinary files, without Node/typed Query eligibility. A directory missing its same-named primary file and an unpaired `.typ` default to Unmanaged; this alone does not stop ordinary traversal or discovery of descendants not explicitly excluded. Explicitly marking a directory subtree unmanaged prevents node discovery/bulk organization from re-entering it, not ordinary file browsing. A complete node's canonical `.typ` cannot be unmanaged independently; leaving node management explicitly previews identity/reference consequences without automatic moves/deletion.

Node structural actions still reject targets inside explicit ignored/unmanaged boundaries or actions over a known subtree containing such exclusions. Ordinary non-node file actions separately preview their exact scope through the same safe backend; they cannot bypass node pairing, registered resources or historical obligations. An admitted node losing its primary file/pairing is a diagnostic/recovery event, never silent demotion, identity retirement or guessed ID birth. Strict exclusion of unobserved additions still requires strong scope capability. Section 5 late-boundary pending rules refer to these explicit exclusions, not merely an ordinary container missing a primary file.

Managed directories provide stable shortcut targets. Node directories use NodeRef. Core `admitDirectory` creates `weftext.directory.json` for a non-Node container, recording only DirectoryId without duplicating parent/name/path. Creation, fresh copied IDs, moves, duplicate IDs and gaps use the same Plan/manifest rules. Creating a shortcut admits only its selected container, not the entire library. Unmanaged boundaries receive no automatic ID. A user may explicitly register only directory navigation identity while retaining its non-Node status and discovery boundaries; this creates no primary file, Node or typed business object. If registration is declined or the backend cannot prove stable directory identity, offer an explicitly weaker locator bookmark, not a rename-stable shortcut. Root `.weftext-tags.json` registers immutable TagId and mutable displayName; TagRef supports stable shortcuts, navigation and Query. Equal names do not merge automatically, and literal label strings do not register objects. Core `createTag` may accompany a note's typed TagRef assignment in one Plan; SOURCE owns the native typed slot.

Portable control data records only facts current files cannot recover: identity creation and retirement, schema history, committed versions and causality, resource-file bindings and Trash restoration information. A resource's stable Ref binds its resource ID to a relative file locator in node-local `weftext.resources.json`; that file does not determine Node parentage. Ordinary noncanonical files remain visible. Unregistered resources do not automatically receive stable IDs. A raw rename without proof of the original object requires explicit rebinding or conflict resolution. Annotation IDs in JSON are separate from their targets and lifecycle.

`.weftext-history/` retains immutable committed manifests and required exact blobs. It supplies history, replication and recovery evidence; it cannot be edited into another current source. Device/session Drafts, active SQLite journal/WAL, runtime credentials and derived indexes reside outside the synchronization root. Between durable commit and manifest publication, the original journal's committed record and complete blobs provide actual evidence of this operation's identities/revisions/results. Startup recovers pending publication first, and backup consistently includes these records; missing history cannot trigger execution again. A historical snapshot can differ from current files; current reads still observe actual files and current authorization. Indexes, search, reverse relations, thumbnails and graphs are rebuildable; rebuilding cannot restore missing execution responsibility or invent IDs.

A complete backup includes ordinary files, ignored bytes, portable control/history and consistently captured local unresolved journals/Drafts. Copying an active SQLite main file alone is insufficient. A content-only backup may be exported separately, with an explicit limitation that it cannot recover missing operation or financial responsibility. Restore on another device creates new local observations and derived indexes. Actual pending execution responsibility comes only from its original journal or an explicit custody transfer.

`BackupLibrary` keeps the original v1 `library/`, `private/`, `backup.json` tree. New ActorOperation, output claims, Drafts and migration records carry optional library provenance as their first metadata field, without a second ownership ledger. Hosted producers bind the trusted configured root, its actual file identity and admitted WorkspaceId; new local Drafts use their original Session root, including an ordinary root with no WorkspaceId. Retained legacy records do not acquire invented provenance. Selection reads bounded metadata on the protected handle before payloads, validates the complete retained proposal/consumption closure, and excludes proved foreign-library bodies. Unknown or mixed scope fails explicitly rather than filtering proposals or exporting the entire shared private directory.

The original frozen backup plan retains selected exact files and one private membership/routing digest, rechecked by execution and original transaction recovery. Only typed, validated evidence from that same backup operation can qualify its own newly created journal files; a matching filename prefix grants no exception. Backup may capture an installing source operation only with its original complete pending evidence and current tree, without resolving it or declaring it committed. Before the first output effect, the original manifest and unique files/directories fit the 64 MiB/5,000-member input limits and the lossless ZIP fits 80 MiB. Encoding consumes only those frozen after-images. The dedicated hosted backup fence lives in the original ActorOperation, independently of general feature/output grants. It does not add an automatic restore decoder or permit original request replay after delivery cache loss.

Native content export separately uses `capture_native_export` to produce package bytes, the manifest and an in-memory `NativeExportWitness` from one capture. Consumers revalidate that same witness before delivery instead of rereading a newer tree as evidence for old package bytes. Authorized managed source, registered resources, annotations, Schema, settings and style retain their original roles. Unmanaged, ignored and Trash bodies are not read and then filtered; only necessary omission paths and physical metadata are observed. Current limits are 5,000 namespace members and 64 MiB of retained inputs. The witness qualifies observed membership and objects without promising a strong negative scope for arbitrary future raw files. Private journals, drafts and credentials are excluded, so this is not a complete recovery backup.

The v1 native package adds the closed `generatedBibliography` role, restricted to `weftext.citations.bib` beside its unique source owner, containing the exact valid UTF-8 Bib bytes generated for this output. It has no NodeId, ResourceId or author revision. Existing members, case aliases or a same-name original reported as omitted cause refusal rather than overwrite. Generation derives from authorized Work publication fields in the original package capture; whole-library output authority does not imply citation use/export authority. Native import retains this derived file only inside the preserved original ZIP, reports `generatedBibliographyNotInstalled`, and does not install it as current author content or a registered resource. The application continues generating citation input from remapped current Works. Older readers explicitly reject the unknown role; compatibility with those readers is not claimed. Actual product acceptance remains defined by the candidate evidence.

### 2.1 Ordinary-file sessions

The local launch document is only an opening locator. Browser reload reads current source, Base and personal recovery Draft from Core instead of replaying a session cached at server startup. Managed notes resolve their original stable identity across qualified renames and moves. Unavailable identity preserves the Draft and reports failure rather than selecting a namesake at the old path. Ordinary files establish a fresh ordinary session at the explicit launch path.

`openFile` opens an outside-library or unmanaged `.typ` without initializing a workspace or inserting metadata; an existing id does not admit a Node. Its target is an actual file object and authorized path scope. FileBasis records original bytes, object/path binding, observation generation and dependency root separately from NodeRef/RevisionId. Reuse Draft, the single-file save backend, operation journal/recovery and conflict checks without inventing WorkspaceId, portable manifests or schema admission. Invalid syntax remains exactly saveable with diagnostics; read/write permission and compilation eligibility are distinct.

The first open uses the visible parent directory as the default project root, adjustable by the user. Resolve relative paths from each real source file and root-relative paths from that selected root. Dependencies require authorized read scope; reject escape rather than mounting the whole disk. Retain official package resolution, explicit offline/network policy and application font defaults; no ambient library style/schema. Editing a dependency opens its own ordinary session.

Save checks the actual object and exact Base, preserving concurrent external drafts; a hash alone is not CAS. Save As defaults to create-only; an existing destination needs its own preview/current write basis, without modifying the original. Qualified platforms reuse the safe backend. WebUI without local write access describes upload-copy/download-Save-As semantics honestly. Recovery drafts live in private application storage, not new control files in the user's directory. Managed files redirect to their Node/Resource session so this route cannot bypass managed contracts. Joining a library explicitly previews the new node, metadata and file arrangement, preserving originals until success.

## 3. Identity, revisions and current reads

Random UUIDv4 remains the identity choice. WorkspaceId and Node/Resource/Annotation/Directory/Tag IDs form fully typed `EntityRef`s, supporting rename-stable references, offline creation and independent copied identities without making names or paths identities. A UUID is a stable random identifier, not a security credential. Directory/Tag add only identity required by navigation; they are neither notes nor per-value fact IDs. Core allocates new identities; source/sidecar IDs are claims. An existing identity must match admitted creation evidence, its current unique file binding and lifecycle. Duplicate IDs, external copies carrying IDs, missing metadata and partial synchronization do not create identities or trigger new IDs automatically.

Initialization uses §5.3 create-only boundaries, not an assumed atomic whole-workspace publication from same-user staging. Durably record the bootstrap operation, WorkspaceId, proposed config/source revisions and exact after blobs first. Under the authorized target-parent closure, create-only the new root/subdirectories using the directory creation-handle primitive in §5.3, retaining its original handles; then CreateNEW/protect each root config, schema, marker and planned source. External tools may see partial files; Core recognizes installing/missing births as incomplete and never activates from marker presence alone. An occupied root conflicts rather than being initialized in place. Only a complete plan/manifest/journal/current authorization reaches one activation commit marker and creator grant; portable publication follows.

Failure preserves the original ID/recovery plan without overwriting replaced objects or recursively removing unknown additions. Rollback touches only proved-owned files and actually empty directories. Lost responses query the original operation, not new Workspace/Node IDs or repeated creator grants. Server initial permissions come from an authorized issuer, never client metadata; restart/restore cannot confer creator grants again. Existing content uses explicit import/admission with originals/unknowns/losses retained, not extension rename.

`RevisionId` is a random identifier privately allocated when freezing a Plan. It becomes valid only at commit. The manifest binds EntityRef, RevisionId, exact blob, causal parent revisions and transaction once. It does not depend on a digest of source containing itself, so final `.typ` can hold self/cross fixed addresses and annotation anchors. Private planned IDs are not published success. A true no-op retains its revision; equal-byte external admission is a new provenance-admission fact.

Each actual source RevisionId admission/CommitManifest also freezes `SourceSchemaBasis=(SchemaRef, committed ConfigRevisionId)`, not another parsed AST/Field mirror. Cold parsing resolves original metadata short keys/types to permanent Field/Type IDs under that basis, then consumes explicitly compatible current schema IDs; it never reinterprets historic source through latest same-named aliases. Body-only/existing-field value edits inherit the original basis by default. Explicit schema/source migration or construction selecting a new schema may rebind, previewing every required key/type spelling change. Copy/import without an original basis cannot guess same-name semantic identity; require explicit mapping or unknown/loss reporting.

`ReadBasis` is this Core instance's current qualification: persistent revision or explicit external observation, observer incarnation, actual file object and change generation, lifecycle, schema/authorization generations and actual dependencies. Hashes verify byte integrity, not object identity, authorization or conditional writes. Watcher gaps, restart, replacement, ABA, partial materialization and relevant dependency changes invalidate old bases. A new read after rebuilding may acquire a new basis; it cannot revive an old plan or selector's write eligibility.

`DependencySet` has one family of typed object, lifecycle, structure/range, schema, authorization, environment and World-read dependencies. Complete negative ranges and absence require current authorized enumeration. Placeholders, I/O errors, hidden objects and unfinished indexes do not mean absence. Unrelated object changes do not invalidate a save depending only on this document. Strong actions requiring complete scopes or constraints must prove their actual scope; ordinary save success proves no workspace-wide completeness.

Authorized raw reads may retain valid or invalid external bytes. Unadmitted external state has no persistent typed write address. An ordinary whole-source save may check that same external Base within a short protected window and explicitly admit it without first compiling the entire body. Save semantics separately report local_valid / semantic_pending. Unproved cross-object conditions cannot be downgraded into successful strong actions.

### 3.1 Local note timeline

The local note timeline belongs to the current local v0.5 completion scope. It browses, by time, the saved source revisions actually retained for one note. Core associates history through stable NodeRef and committed revision facts. Core-managed renames and moves retain the same note; path/title never merge another note or an external namesake. Reuse existing Core history, exact bytes and recovery mechanisms without another version store. Uncommitted/unresolved journals and Drafts remain separate from saved revisions; recovery proposals cannot impersonate saved records. Business Query timelines for tasks, events and similar data are a separate domain.

The list discloses its actual retention scope, the evidence for each revision's save time and its availability. Missing save times explicitly show “time unknown”; file mtime, scan time and UUID order cannot impersonate commit time. Unretained, missing or unreadable history is explicit, without substituting latest for the selected old revision or treating an empty list as proof that no save ever occurred. Retention follows the history/recovery responsibilities in §§2/9.2, without promising permanent preservation of every keystroke or every revision.

Record actual save times within existing commit records and derives a rebuildable list. Old records without timestamps stay unknown; there is no separate timeline ledger. Device clocks provide display times only: ties or clock rollback do not change proven commit relationships. Local coverage comprises this library/note's still-retained revisions saved or explicitly admitted by Core, without promising unadmitted external edits, every keystroke or unimported other-device history. External renames/moves first require identity continuity from the existing recovery process; unresolved identity is reported rather than joined by path or name.

Old revisions open read-only. Comparison fixes the selected historical revision and a newly read current saved revision. If an unsaved Draft exists, explicitly identify the comparison target as “current saved revision” or “current Draft snapshot” and protect the Draft. Browsing/comparison cannot replace the edit buffer or clear Undo/Draft. Historical semantic reads use this section's original SourceSchemaBasis. Missing original configuration/dependencies make the corresponding preview/semantics explicitly unavailable while authorized exact source bytes may remain readable.

Restoring the selected old revision creates a new ordinary save proposal, preserving later history rather than rewinding/truncating the revision chain or directly overwriting current files. First explicitly save, retain or merge any unsaved Draft; then freeze the proposal against the current object, current Base and write eligibility using the same Core operations, idempotency and protection against overwriting concurrent changes. An unknown restoration response queries the original operationId/Plan rather than rebuilding and blindly retrying. History read access grants no restoration write permission; unresolved recovery uses the existing mechanism first.

The local candidate derives history from `savedAtUnixMs`, `commitSequence` and original operation/version evidence in existing save/transaction commits; the version key references the original save operation, without a new ledger. Browser controls expose exact source, comparison with current saved bytes or a Draft snapshot, and restoration through the original save path. Protecting Drafts retains the current buffer and existing recovery variants with their original bases. Applying a restore receipt updates Base while preserving an original dirty buffer or input made in flight and the shared Undo history. Every postsubmission error first reconciles the original operationId; only a confirmed unregistered rejection releases it. Receipt-application or Draft-persistence failure retains that operation. Current historical preview is exact source/text diff only, never a rich historical rendering using current dependencies; restored business semantics require revalidation. Actual acceptance uses ROADMAP LHT01–06. Multiuser history access/restoration and synchronized presentation remain v0.6 work.

## 4. Frozen plans and exact results

`prepare` receives operationId, typed Intent, Draft Base and budget. Core authorizes the actual potential scope before reading. The Plan retains actual read/write sets, complete before images, exact after blobs, identity/revision allocation, structure capture paths, constraints, actual transforms, schema and the permitted user preview. Caller offsets, IDs, authorization flags or digests are not proof.

SOURCE produces narrow edits from the official AST and original bytes. EDITOR owns Draft sequence, selection, Undo and the safe writable subset. FEATURES owns Query, copy/template transfer and business postconditions. Core materializes every target with one map, reparses the complete after sources, and validates every actual typed reference, fixed revision, annotation range and preview match. Generated content being readable/queryable does not give it a writable address. An unanalyzable transfer preserves content and explicitly reports unavailable transfer semantics; it does not replace strings in unknown code.

One object-key-to-final-EntityRef map covers fresh/copied/existing objects; each item states disposition, source and owner. Three different result arrays are unnecessary. An independent actual change set lists genuinely changed source, structure, lifecycle, annotations and schema. Mapping an existing object does not prove a new revision. A fresh object's before is absent; a missing field in an existing Node does not make that Node absent.

operationId is unique within the workspace's current operation-origin domain, with its complete canonical Intent fingerprint fixed. The same ID and request returns original status/result; changing input under the same ID conflicts. Preparation/staging is not saved. Planning failures retain Draft. A revised proposal uses a new operation linked to the original Draft, so retry cannot silently change source, targets or allocations.

## 5. Default local saves and backend contract

Desktop does not require a checkout for each save. The initial choice is a short exclusive content-write window on Windows local NTFS. Qualification is specific to the actual volume/filter/path; cloud placeholders, network drives and aliases are not qualified by using the same API. Existing-file content updates and directory namespace operations use different protection methods.

**Existing-file content update.** The backend obtains a read/write handle denying shared read, write and delete, and proves canonical containment, absence of reparse/uncontrolled hard-link aliases, and path/object binding. It reads complete current bytes through that same handle and compares them to Draft Base and Plan before. The handle stays open through complete after writing, flush and durable commit. This avoids closing the guard and then performing hash/rename. An external editor's existing writer yields a sharing conflict: retain Draft, retry within bounds and explain that the file is busy. External new bytes discovered after acquisition conflict rather than being overwritten.

Windows sharing modes check existing access and restrict later write/delete, including the documented writable-mapping conflict. This makes same-handle verification followed by in-place writing a testable candidate. It does not automatically prove ancestor stability, filter behavior, exclusion of new directory entries or power-loss durability; those need separate coverage. Byte-range or advisory locking alone is insufficient. [Official CreateFile documentation](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilea)

Complete in-place writing is not crash-atomic for one file: the journal first retains complete before/after images, but a crash can leave partial bytes. Core reader barriers prevent current reads of half-written content; restart checks recovery first. Ordinary external tools may see partial bytes after Core terminates, so both content and recovery journal must be retained. A replace-based backend qualifies only when exclusion remains held and actual displaced bytes are proved; read-hash-rename is not CAS.


### 5.1 Building the closure

1. Fix Workspace/volume identity, source Ref/object, source/target parents, basename and required permissions. Resolve relative paths from an authenticated volume root rather than reinterpreting a mutable DOS drive alias. Reject escapes, unknown mounts, reparse/symlink and nonunique hard-link aliases. Check directory object type as well.
2. Collect every directory chain from the trusted volume/workspace root to source, source parent and target parent. Each backend must state why location above the workspace root is stable; an old absolute string is not a root. Acquire one guard per physical directory object and reuse shared ancestors, avoiding conflicting duplicate DELETE handles.
3. Compute access from path roles first, then acquire root to leaf. A Windows directory handle needs actual `FILE_LIST_DIRECTORY` read-data access and `FILE_READ_ATTRIBUTES`, sharing `READ|WRITE` but not DELETE. The source's same guard includes DELETE on its initial open when it will be moved. Attribute-only access is not exclusion. Do not later reopen a DELETE handle conflicting with an existing no-shareDELETE guard; an access-role upgrade requires side-effect-free replanning.
4. Verify each child volume/object/type through its actual parent directory entry, then compare the child handle. Validate the complete current chain and original source binding. Use `OPEN_REPARSE_POINT` to open reparse points themselves and reject unauthorized resolution; subsequent operations use the proved parent/name. Failure to acquire a guard or mismatch releases all protection and retains Draft for bounded retry/conflict. Never release guards and then write using an old path string.
5. The target name is prospective; earlier enumeration does not prove absence. Final create/rename uses atomic create-if-absent/no-replace. A raced name conflicts with both sides preserved. Directory guards stabilize the directory itself and its ancestor location, not child creation.

Hold all guards through actual operation, verification and durable commit. Rename through the source guard that already has DELETE, keeping target-parent guards; do not close the source and move by path. Use the actual target-parent handle for relative naming where required; a verified volume-path API may be used while the whole chain is guarded. The backend must verify this API combination separately; SQL locks establish none of it.

### 5.2 Overlap, moves and Node renames

An ordinary same-volume move is one no-replace rename of the bound directory object with unchanged basename. Earlier additions/edits travel with its actual tree; later changes are new external observations. Receipt proves placement, not frozen tree bytes or a source revision. Trash/restore similarly move the original directory to a unique batch/authorized empty target, retaining tree/bytes/restoration facts without recursive deletion.

Reject a destination parent equal to the source object or within its descendant chain. A source/target at the actual same location is a qualified no-op; an identically named different object is not. Shared parents use one guard. Cross-volume moves use explicit copy plus conditional Trash, not same-object rename.

Node `A/A.typ→B/B.typ` remains two steps. Record exact directory/canonical-leaf objects, names and recovery responsibility. After no-replace leaf rename, close the leaf handle if it prevents outer rename, retaining the directory guard and complete ancestor/target-parent closure. After outer rename, reacquire the actual canonical file guard and validate object/control role and declared external changes. New leaf/root third states are pending, never overwrite rollback targets. This leaf-release window gives no lasting old-source write qualification and claims no frozen tree content.

Continuing a descendant's history or Query identity also requires exact member-placement evidence in the original Relocate. Select relevant members from existing birth/directory-admission facts and record their relative positions, stable IDs, physical file/directory objects and parent objects, without scanning private source or creating another placement ledger. This evidence does not add whole-tree byte CAS to ordinary moves; legitimate late edits and additions still travel with the original tree. Execution and original-operation recovery must verify member objects before recognizing their placement continuation. A legacy ancestor-move record containing only path prefixes cannot prove that a descendant traveled with it. A former descendant cannot borrow a move of another object occupying the old address; unproved identity remains explicitly pending.

Ordinary source save also uses its parent/ancestor closure plus an RW share0 file guard, checking Base and writing/flushing/committing through one handle. Guarded ancestor/target-parent changes cannot redirect the write after its last check. Busy retains Draft. The guard set is finite, not a workspace-wide lock.

### 5.3 Copy and templates: fixed snapshot members without invented private isolation

The ordinary Windows backend does not treat a same-user private folder as isolation. A Plan fixes source snapshot members/exact blobs, one fresh map, target directories/files and budgets. The snapshot uses admitted logical-cut revisions or explicitly selected authorized observations. An unproved complete-subtree request has partial coverage/pending status rather than silently copying fewer members.

For hosted copy/template, Server separately authorizes whole-subtree read and export before capture. Core's opaque FeatureTreeWitness fixes the exact owner, source file/directory membership, physical identities, parents, bytes, original Schema and root controls, with bounded members and retained bytes. Transfer inventory comes only from this authorized cut and the original authorized contexts of explicit inputs, without whole-library inventory or unrelated source reads. Destination-parent namespace evidence does not authorize reading reference targets. Unproved ordinary external path links retain their values with explicit copy losses; a typed reference requiring target proof rejects copyRef when that context is missing. A stable reference alone never authorizes reading its target. The original Plan still owns persistence, commit and recovery. The witness itself grants no new permission.

A preconfigured hosted destination slot is bound by the original FrozenOperation's optional hosted_destination selector, never inferred from the source anchor. Only original hosted structure preparation sets it; local producers, legacy records and other producers retain the default, without historical backfill. Original birth evidence for create/copy/template, or the original Relocate leaf identity for rename/move/restore, combines with the current admitted object and exact placement to qualify the slot. An identical name, identical bytes or a separate local creation cannot claim it. Reading the result still requires independent current Server read authority.

Installation:

1. After the journal and exact blobs are durable, acquire §5.1 target ancestors/parents and Core scope reader barriers. Reserve simultaneous handle capacity for all planned files before installation. Insufficient capacity fails or produces an explicit revised batch plan before writing anything.
2. Create each new planned directory and obtain its original guard in one backend call, not `mkdir → reopen`. The Windows candidate uses [NtCreateFile](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntcreatefile) with `RootDirectory` bound to the held target-parent handle and a single relative component, `FILE_CREATE`, `FILE_DIRECTORY_FILE | FILE_SYNCHRONOUS_IO_NONALERT | FILE_OPEN_REPARSE_POINT`, LIST_DIRECTORY/READ_ATTRIBUTES/DELETE/SYNCHRONIZE access and READ|WRITE sharing without DELETE. Require success and `IO_STATUS_BLOCK.Information=FILE_CREATED`, journal the returned object evidence and retain that same handle as the new closure member. An existing same-named directory conflicts; do not merge into it. Initial workspace root uses the same call against its authorized external parent. Ordinary external tools may see the directory early; Core readers see incomplete/installing. A finite local NTFS probe exercised this returned creation handle, same-name collision and blocked external root rename; production platform/durability qualification remains pending. A backend offering only mkdir/reopen cannot manufacture creation ownership and must use an actual equivalent primitive or leave this scope pending.
3. `CreateNEW` each planned file RW share0. Write the exact after bytes, set exact length, flush and reread through that creation handle. Hold every such handle through commit, without closing for hash/replace. A raced target filename conflicts rather than being replaced. Creation handle plus journal establishes ownership of the new object.
4. Verify every planned target, fresh identity/reference map and constraints. Commit only when every selected snapshot object exists correctly. A pure copy's after is that fixed membership, not exclusion of third-party raw additions to its target directory. Unknown additions are independent external objects: no copied-result entry, automatic ID/typed admission or deletion. Delivery may report `external_pending`. A strong intent requiring an exclusive complete postscope is not fulfilled by this weaker condition.
5. Persist the marker fixing all planned objects/Receipt, then release file/directory guards. Rescanning retains actual external additions, while the snapshot Receipt remains original. Extra raw files cannot disguise a missing planned output.

Sync transports exactly this operation's copied changes/births and blobs, not recursive replacement of the target tree. Receivers also create-only and verify local identity/object conflicts. External target additions are not automatically included in the manifest; observe/admit them separately. Occupancy or identity conflicts cannot be solved by issuing new IDs.

Failure/rollback touches only explicitly created objects still proved owned by this plan. Preserve file third states. Even handle-based directory removal requires actual emptiness. An unknown addition causing removal failure retains the real target tree with an explicit pending recovery entry, not recursive cleanup. Multi-root templates use the same rule; partial execution is not total success. This default requires no hidden DACL/service privilege and provides no instantaneous external multi-file atomicity.

### 5.4 Purge: fixed confirmed objects and actual empty-directory deletion

Purge remains authorized and destructive. Fix the root, confirmed bytes/membership and reject known ignored/unmanaged boundaries first. An ordinary local tree has no exclusion of raw additions; use preservation rather than naming a folder controlled staging:

1. Obtain the directory closure in the actual Trash tree and retain confirmed Ref/file objects/bytes and recovery records. Acquire every confirmed file RW|DELETE share0 before deleting any. Existing writers/mappings/busy cause zero deletions and bounded retry. Known subdirectory identities also belong to the guard set.
2. After durable installing, set disposition on exact file handles and flush/close as required. Do not recursively delete mutable paths. Journal actual deletions and original-ID recovery responsibility. Retain necessary before data until commit; half-deletion is not success.
3. Delete original confirmed directories bottom-up with handle-based `delete-if-empty`. New raw children make the OS return directory-not-empty and remain in the actual Trash tree. Unknown children never enter the deletion set. Guards stabilize the directory; the deletion primitive performs atomic emptiness checking rather than `list empty→recursive delete`.
4. Commit successful purge only after every originally requested directory has been removed and tombstones/responsibility are complete. Nonempty/busy returns pending_reconciliation with exact processed objects and real residual content under the original operation ID, never whole-tree cleared. Recovery only resumes the original explicit set or recreates provable objects no-replace. Unknown residuals are never deleted or overwritten.

A quiescent normal local Trash can finish purge; concurrent new drafts survive for an explicit decision. No exclusive whole-namespace guarantee follows. Deployments needing atomic whole-tree erase or strong business negative scopes use an independently permissioned/fenced Server writer, not same-user ACL naming.

Known ignored/unmanaged boundaries reject the action without re-entering them. A late boundary discovered after rename but before commit retains the actual tree as pending, never overwriting a third object at the old path. A new boundary after commit is a later external observation; it cannot revoke the original historical Receipt or execute the move again. Absolute absence of boundaries/unique values under arbitrary raw additions is a strong negative-scope contract, not proved by local directory guards. Ordinary same-object moves, fixed-snapshot copies and safe purges have their own precise completion conditions instead of all becoming unavailable.

**Server and later platforms.** A Server writer service owns an OS-isolated directory; ordinary clients and workers cannot write it directly. It fences every actual file action and journal decision. This deployment can provide strong namespaces and automatic recovery. Ordinary Linux advisory locks cannot stop arbitrary tools of the same user. The initial Linux backend can support a controlled service directory or an explicitly exclusive host mode; an open local write backend requires separate proof. Network filesystems require individual qualification. Optional checkout and three-way return serve long external editing or unqualified backends, preserving original Base/current/proposed; checkout is not mandatory for normal Desktop saves.

The contract need not resist a disk owner deliberately bypassing isolation, damaging journals or a malicious kernel. Ordinary editor/sync races, existing handles and mappings are within the validation scope. Out-of-scope behavior does not justify claiming safety against arbitrary external writes. Without required protection, retain the draft and return the actual operation boundary; never silently downgrade to an observed-only save that may overwrite an unseen draft.

## 6. Executable commit and recovery algorithm

1. Read the original operation/canonical Intent fingerprint. Same ID/request resumes/replays; changed input conflicts. Durably retain the fixed Plan, actual objects, recovery responsibility, needed before/after blobs and budgets. Draft retention is not saved.
2. Acquire §5 directory closure, file guards and scoped Core reader barriers. Validate binding, authorization, schema, lifecycle and actual dependencies. Failure preserves Draft for bounded no-change retry. No rename occurs here. Ordinary moves do not freeze child bytes; copy fixes snapshot members, purge fixes confirmed objects, strong business actions require complete scopes.
3. Atomically journal and flush the complete frozen Plan and installing before any rename/create/delete. SQLite establishes the journal decision, not external installation.
4. Execute §5 same-object moves, Node two-step renames, create-only outputs or explicit-object disposition. Byte writers retain handles through write/flush/reread; namespace steps verify actual objects/destination and directory-entry durability. Step records do not replace ownership. Busy/disk-full/revocation/cancellation/third states stop further steps while retaining original-ID responsibility.
5. Within the barrier, verify the full original Intent and current authorization/dependencies, then one durable marker fixes transaction, actual valid RevisionIds, Receipt, SourceSchemaBasis, logical generation/cut facts, author Job steps and publication outbox. Move proves placement without source revision; copy requires every fixed target; purge requires all requested directories actually gone. Partial outputs/residuals are not subset success. Release guards, then index/publish asynchronously; pending manifests do not undo saved status.
6. Resolve unknown via operationStatus on the original ID, never new identities/charges. Synchronization published, Job complete, HTTP200, Draft retained and saved are distinct states.

Core readers gain atomic multi-object logical commit visibility. Ordinary external tools may see intermediate steps, without an instantaneous multi-file atomicity guarantee. Between committed journal and portable publication, the original journal/blobs establish qualification; startup/backup capture that window consistently.

Recovery reads the original durable decision before classifying actual objects as before/after/third/unavailable. Require exact objects, installation ownership and bytes; matching hashes/file IDs do not restore continuity. A continuously fenced Server writer may resume. Open-local crashes release guards; uncertain residuals first preserve current/before/after for explicit repair/merge, without automatic overwrite. Copy/bootstrap rollback never removes unknown children; purge recovery never expands its confirmed set; directories use delete-if-empty or no-replace return. Already committed r5 Receipts survive later r6 stale business bases, with current disclosure filtering. Revocation does not turn completed facts into effects to resend; unrelated scopes continue. Undo is a new currently qualified Plan.

### 9.1 Shared LogicalCut and current publication


#### 9.1.1 Sole producer and opening algorithm

The Core commit marker atomically advances one journal generation with every admitted source/config/lifecycle/placement fact of that generation. A multi-object transaction has one generation. Its per-entity cut view comes from actual committed facts/retained blobs, not a sequence of `read current` calls.

`openLogicalCut(scope,purpose,budget)`:

1. Verify the caller's current potential scope and minimum disclosure. Acquire a short commit/read barrier and wait for relevant Core installations to become committed or explicitly unavailable; never read half-installed state.
2. In one journal read transaction, obtain decided generation `g`, complete admitted causal heads, exact per-entity RevisionId/blob/lifecycle, historical directory view and schema/rules/settings revisions. Scope membership/negative ranges require complete admitted inventory proved at that `g`. Building indexes or unknown raw boundaries do not mean empty. Directory/config views derive from original operation facts; source revisions include SourceSchemaBasis, and retention protects the corresponding original configurations.
3. In that transaction register cutHandle audience, authorization generation, dependencies/coverage, finite TTL/budgets and exact blob/config/history retention roots; then release the barrier. GC cannot remove data between capture and lease registration. Pending manifest publication is satisfied by the original committed journal, without waiting for networking.
4. `readEntity(ref,at=cutHandle)`, `readScope(at=cutHandle)`, schema and World reads use only fixed cut versions. Missing blobs/configuration make that cut unavailable/partial; never substitute latest. A cut handle authorizes snapshot reads, not current writes; Actions need fresh prepare.

### Local sync consumers and original proposal cancellation

Local sync APIs separate pairing, enablement, status, publication, directory receive/export and exact version-file reads. Clone/apply/merge reuse the original OperationRequest/Preview/Receipt flow. Status reads neither publish nor install; installed portable revisions and the received graph remain separate. Dependency diagnostics compare historical prerequisites with the current graph and do not block unrelated objects merely because an old commit differs. File inspection qualifies the specified object, its exact admitted revision and member, including retained ancestors outside current branches or common bases. It returns the separate original fileRevision, without substituting a newer revision, guessing a filesystem path or executing content. All endpoints require the local owner; hosted actors do not acquire this capability.

`sync/history` pages one explicit object's received records with their original commit, parents, before, revision, state and actual admission. Pages default to 25 and allow at most 100 records, subject to a serialization budget. Commit digests are pagination cursors, not chronological or causal ordering. Coverage states whether all currently received records for that object are admitted; it does not assert that all remote history has arrived or that local files have been installed. nextCommit separately indicates another page. If records arrive during pagination, refresh from the first page instead of treating concatenated pages as a durable snapshot. Missing and rejected records retain their diagnostics but cannot expose their bodies. The browser history entry is read-only and cannot submit an ancestor as a current conflict branch. Actual product verification remains in the candidate record; connected code alone is not acceptance.

`AdoptSyncExternal` distinguishes causal predecessors from observed physical input: `expectedInstalled` fixes each selected object's exact installed revision, while `changes` carries original observed snapshot bases with identical before/after bytes. It only adopts existing current external edits. `sync/adoption-cut` reads explicit selections through original local locators, without guessing local placement from received paths. The complete local HTTP JSON is limited to 16 MiB; browser storage may be smaller and failed persistence must stop before the first prepare request. Ordinary Save/Apply retains its external-change conflict checks. Unselected object members, current Schema/rules and required typed-reference dependencies remain subject to the original scope checks. Unsupported structural or semantic decisions preserve originals and fail explicitly; this action cannot perform an arbitrary simultaneous rewrite.

Ordinary Save and transaction publication also check the original installed physical observation. Reopening a fresh Base cannot admit an external same-byte write. A same-byte write committed by Core remains valid through its exact observation continuity; missing old evidence cannot be filled from current observations.

The current adoption slice returns `syncSemanticDecisionRequired` for citation Work, saved-query or embedded-query semantic dependencies. Client confirmation or old parsing results do not establish revalidation; ordinary unresolved native links remain legal. Complete semantic decisions remain required implementation in this same v0.6 milestone.

New enable Plans retain initial leaf physical bindings; clone/apply establish local evidence through original observations. Legacy plans without physical evidence report unavailable instead of backfilling old qualification from the current path occupant. Files, parents or dependencies changing after preparation invalidate commit while preserving the original request and drafts. Adoption reuses the original durable Plan, commit decision, outbox and recovery, without a second current-state or execution ledger. Default Schema/rules require genuine absence with an original negative dependency; a later file cannot bypass validation through a bundled fallback. Success registers a new revision of the exact current bytes without silently selecting historical branches or uninstalled versions.

The browser persists its exact request before preparation/confirmation. Status reads never execute; lost preparation retries the original request. Original-ID lookup returns Core's retained request and current preview even after a browser origin change. The new cancelPrepared action applies only to the exact planId of an original sync transaction. Committed/resolved outcomes are idempotent; an installation marker requires original recovery and refuses cancellation. Before installation, cancellation writes only a durable resolution, without checking or modifying current author files. An externally outdated proposal can therefore be abandoned while a late original execute is fenced. This differs from keepCurrent's complete original-participant recovery proof and cannot bypass recovery after installation may have begun.


### Same-owner hosted transport consumer

Server's separate syncOwner capability grants full immutable-record transport only for its explicit syncIdentity. It is not inherited from document/field rights and grants no raw paths, private-state access or author-tree installation. Persistent policy binds the pairing; actor/epoch/ticket and each block's delivery/receipt are revalidated under the same service lock. Revocation clears epoch caches and regrant does not revive old tickets. Authorized saves on an already bound physical replica retain the original Core outbox; receiving manifests never changes the relay's current author tree. Uploads are idempotent by complete record digest. Partial records are bounded disposable memory buffers; complete records persist in Core's original immutable store. Transfer progress is not an author receipt. Downloads freeze record bytes instead of substituting latest content during continuation.

The local network client copies only within an exact pairing and bounded record catalogue; network waits never hold the Core writer mutex. Each completed record is revalidated by Core. Interrupted/restarted transfers retain completed records, while installation still uses existing Plan qualification and recovery. This transport trusts owner devices/accounts. TLS, permissions and digests separately establish transport confidentiality, disclosure authority and integrity; they are not a device-signature or malicious-provider protocol.
