# Typst Core: files, commits and operating boundaries

Status: **current Core contracts, with implementation and acceptance distinguished by slice**. Independent design acceptance of the fixed earlier baseline remains historical; refinements and experiment limits are recorded in [REVIEW](REVIEW.md) §8. Connected code establishes neither product availability nor complete v0.6 acceptance.

## 1. One file workspace and one author commit path

Weftext's native Rust Core serves Desktop, CLI, Server, WebUI and future Mobile. Local Desktop/CLI call local Core; their remote modes and WebUI call Server only. Offline hosted clients may retain Drafts but cannot grant themselves hosted commit eligibility. Mobile local writes require a qualified platform backend. Real-time collaboration remains later work; future OT/CRDT also submits an explicit author proposal.

Ordinary saves, field edits, creation, moves, copies, Trash, restoration, annotation suggestions, templates and business actions all use Core `Intent → Plan → OperationJournal → Receipt`. UI, converters, agents, synchronization and indexes have no second author write entry. Conversion and external execution use recoverable Jobs; a Job's workspace changes still enter the same Plan.

Persistent writes are ordered by actual conflict scopes. Multiple users may read, edit, retain Drafts and prepare concurrently. A physical replica's final durable commit coordinator may serialize briefly; this does not mean prolonged workspace-wide blocking or a single user. Different replicas may commit ordinary content offline without duplicating external execution responsibility.

## 2. Sole file and structure authority

A managed Node is `X/X.typ`. Its body, declaration, fields and author styling reside in that Typst source. SOURCE's explicit author roles define title and subtitle; no title is valid, and filename is only a display fallback. Resources are ordinary files; independent annotations use `weftext.annotations.json`. There is no second body or shared presentation database.

The exact root `.weftext-format` bytes are `weftext.typst.v1\n`. One `.weftext-workspace.json` records WorkspaceId, current schema and storage-contract selection. The marker selects a format; it grants no identity, permission or historical continuity. Directories without a valid contract are unmanaged, incompatible or incomplete as appropriate; no format guessing or automatic conversion occurs.

The directory tree is the only parent/name/path authority for live Nodes. Portable metadata does not maintain independently editable parent/children lists. Authored sibling navigation order uses the original Settings under §2.4, without changing parentage or personal list sorting. The actual Trash directory tree defines its internal structure. A Trash record may retain the original location, batch and restoration membership because these are historical and restoration facts; they cannot override the live tree. An occupied restoration target conflicts rather than being overwritten.

`.weftext-rules` does not inherit `.gitignore`. One Core inventory separately records existence/visibility, Folder Node eligibility and explicit node-discovery boundaries. Ignored entries are hidden from ordinary lists and excluded from discovery, but remain backup bytes. Unmanaged entries remain visible, expandable and openable as ordinary files, without Node/typed Query eligibility. A directory missing its same-named primary file and an unpaired `.typ` default to Unmanaged; this alone does not stop ordinary traversal or discovery of descendants not explicitly excluded. Explicitly marking a directory subtree unmanaged prevents node discovery/bulk organization from re-entering it, not ordinary file browsing. A complete node's canonical `.typ` cannot be unmanaged independently; leaving node management explicitly previews identity/reference consequences without automatic moves/deletion.

After root, Workspace and rules qualification, each complete inventory reads the original Birth evidence of all committed Plans once, retaining physical binding observations in their original order for this call. Each file still qualifies its current protected handle, identity, source declaration and relevant pending operations. A later corrupt Birth cannot be hidden by an earlier valid binding. This observation is never reused across scans and grants no commit authority; the next scan reads original evidence again. Unrelated Plans do not trigger target-path install/commit/resolution reads; relevant Plans retain their original qualification order and alias boundaries.

One accepted-revision lookup enumerates observation record names once while retaining the original journal directory guard. Every committed Plan reads its original records through the same protected reader in the observed order. Required missing or invalid records still reject; exact stamp and byte hash, first matching fact within each Plan, durable commit sequence and maximum-sequence ambiguity rules remain unchanged. Before either a revision or absence is accepted, a second complete enumeration must confirm the same relevant record-name set. Changed names reject instead of adopting new records. Neither record names nor revision results are cached across lookups.

Node structural actions still reject targets inside explicit ignored/unmanaged boundaries or actions over a known subtree containing such exclusions. Ordinary non-node file actions separately preview their exact scope through the same safe backend; they cannot bypass node pairing, registered resources or historical obligations. An admitted node losing its primary file/pairing is a diagnostic/recovery event, never silent demotion, identity retirement or guessed ID birth. Strict exclusion of unobserved additions still requires strong scope capability. Section 5 late-boundary pending rules refer to these explicit exclusions, not merely an ordinary container missing a primary file.

Managed directories provide stable shortcut targets. Node directories use NodeRef. Core `admitDirectory` creates `weftext.directory.json` for a non-Node container, recording only DirectoryId without duplicating parent/name/path. Creation, fresh copied IDs, moves, duplicate IDs and gaps use the same Plan/manifest rules. Creating a shortcut admits only its selected container, not the entire library. Unmanaged boundaries receive no automatic ID. A user may explicitly register only directory navigation identity while retaining its non-Node status and discovery boundaries; this creates no primary file, Node or typed business object. If registration is declined or the backend cannot prove stable directory identity, offer an explicitly weaker locator bookmark, not a rename-stable shortcut. Root `.weftext-tags.json` registers immutable TagId and mutable displayName; TagRef supports stable shortcuts, navigation and Query. Equal names do not merge automatically, and literal label strings do not register objects. Core `createTag` may accompany a note's typed TagRef assignment in one Plan; SOURCE owns the native typed slot.

Section 2.3 defines the v2 parentage, operation, retained-data and sync-admission contracts now connected in the 0.6.3-rc.1 working tree, with whole-version acceptance in progress. Alpha.3's flat v1 registry remains a fact of that earlier candidate.

Portable control data records only facts current files cannot recover: identity creation and retirement, schema history, committed versions and causality, resource-file bindings and Trash restoration information. A resource's stable Ref binds its resource ID to a relative file locator in node-local `weftext.resources.json`; that file does not determine Node parentage. Ordinary noncanonical files remain visible. Unregistered resources do not automatically receive stable IDs. A raw rename without proof of the original object requires explicit rebinding or conflict resolution. Annotation IDs in JSON are separate from their targets and lifecycle.

`.weftext-history/` retains immutable committed manifests and required exact blobs. It supplies history, replication and recovery evidence; it cannot be edited into another current source. Device/session Drafts, active SQLite journal/WAL, runtime credentials and derived indexes reside outside the synchronization root. Startup recovers pending publication first, and backup consistently includes these records; missing history cannot trigger execution again. A historical snapshot can differ from current files; current reads still observe actual files and current authorization. Indexes, search, reverse relations, thumbnails and graphs are rebuildable; rebuilding cannot restore missing execution responsibility or invent IDs.

A complete backup includes ordinary files, ignored bytes, portable control/history and consistently captured local unresolved journals/Drafts. Copying an active SQLite main file alone is insufficient. A content-only backup may be exported separately, with an explicit limitation that it cannot recover missing operation or financial responsibility. Restore on another device creates new local observations and derived indexes. Actual pending execution responsibility comes only from its original journal or an explicit custody transfer.

`BackupLibrary` retains the v1 `library/`, `private/`, `backup.json` tree. Current file Drafts start with required qualified `scope`; file-save ownership is frozen in the same original Plan. Actor/output authority headers are separate from author-library ownership, without another ownership ledger. Selection reads bounded metadata on the protected handle before payloads. File-save actor records use the same Plan classification. Proved foreign bodies are not read; unknown or contradictory scope fails explicitly, without adopting old material by current paths or exporting the whole shared private directory.

The original frozen backup plan retains selected exact files and one private membership/routing digest, rechecked by execution and original transaction recovery. Only typed, validated evidence from that same backup operation can qualify its own newly created journal files; a matching filename prefix grants no exception. Backup may capture an installing source operation only with its original complete pending evidence and current tree, without resolving it or declaring it committed. Before the first output effect, the original manifest and unique files/directories fit the 64 MiB/5,000-member input limits and the lossless ZIP fits 80 MiB. Encoding consumes only those frozen after-images. The dedicated hosted backup fence lives in the original ActorOperation, independently of general feature/output grants. It does not add an automatic restore decoder or permit original request replay after delivery cache loss.

Consumers revalidate that same witness before delivery instead of rereading a newer tree as evidence for old package bytes. Authorized managed source, registered resources, annotations, Schema, settings and style retain their original roles. Unmanaged, ignored and Trash bodies are not read and then filtered; only necessary omission paths and physical metadata are observed. Current limits are 5,000 namespace members and 64 MiB of retained inputs. The witness qualifies observed membership and objects without promising a strong negative scope for arbitrary future raw files. Private journals, drafts and credentials are excluded, so this is not a complete recovery backup.

The v2 native package contains the closed `generatedBibliography` role, restricted to `weftext.citations.bib` beside its unique source owner, containing the exact valid UTF-8 Bib bytes generated for this output. It has no NodeId, ResourceId or author revision. Existing members, case aliases or a same-name original reported as omitted cause refusal rather than overwrite. Generation derives from authorized Work publication fields in the original package capture; whole-library output authority does not imply citation use/export authority. Native import retains this derived file only inside the preserved original ZIP, reports `generatedBibliographyNotInstalled`, and does not install it as current author content or a registered resource. The application continues generating citation input from remapped current Works. Older readers explicitly reject the unknown role; compatibility with those readers is not claimed. Actual product acceptance remains defined by the candidate evidence.

The v2 native content package also adds a closed `Tags` role, restricted to a complete valid v2 forest at root `.weftext-tags.json`. Export captures the original Core-admitted complete tree and same witness. A current v1 registry must be explicitly upgraded first rather than rewriting its blob during export/copy. Cross-workspace import defaults to fresh target-Core identities for the whole forest and retains required ancestors, updating Tags in the same ImportNative/CreateTree Plan. The current native content package is **v2**: losses and product explanations use the shared typed message contract while retaining machine codes, locations and complete parallel diagnostics. Version-1 packages explicitly fail with `unsupportedVersion`; original old ZIPs are retained without automatic upgrade or an old decoder branch. This package version is independent of format markers, the Tag forest and complete recovery backups.

### 2.1 Ordinary-file sessions

The local launch document is only an opening locator. Browser reload reads current source, Base and personal recovery Draft from Core instead of replaying a session cached at server startup. Managed notes resolve their original stable identity across qualified renames and moves. Unavailable identity preserves the Draft and reports failure rather than selecting a namesake at the old path. Ordinary files establish a fresh ordinary session at the explicit launch path.

`openFile` opens an outside-library or unmanaged `.typ` without initializing a workspace or inserting metadata; an existing id does not admit a Node. Its target is an actual file object and authorized path scope. FileBasis records original bytes, object/path binding, observation generation and dependency root separately from NodeRef/RevisionId. Reuse Draft, the single-file save backend, operation journal/recovery and conflict checks without inventing WorkspaceId, portable manifests or schema admission. Invalid syntax remains exactly saveable with diagnostics; read/write permission and compilation eligibility are distinct.

The first open uses the visible parent directory as the default project root, adjustable by the user. Resolve relative paths from each real source file and root-relative paths from that selected root. Dependencies require authorized read scope; reject escape rather than mounting the whole disk. Retain official package resolution, explicit offline/network policy and application font defaults; no ambient library style/schema. Editing a dependency opens its own ordinary session.

Save checks the actual object and exact Base, preserving concurrent external drafts; a hash alone is not CAS. Save As defaults to create-only; an existing destination needs its own preview/current write basis, without modifying the original. Qualified platforms reuse the safe backend. WebUI without local write access describes upload-copy/download-Save-As semantics honestly. Recovery drafts live in private application storage, not new control files in the user's directory. Managed files redirect to their Node/Resource session so this route cannot bypass managed contracts. Joining a library explicitly previews the new node, metadata and file arrangement, preserving originals until success.

### 2.2 Private Drafts and relocation recovery

Within the same actor's original `drafts` directory, required original `FileIdentity` and required `QualifiedInputScope` derive one flat primary-record key. That primary is the sole recovery authority for its exact object/library scope, including clean state and explicit discard or merge results. Ordinary directories can explicitly belong to device input; library input requires an admitted WorkspaceId and original root FI. Records never grant authority across actors or libraries. Old records missing scope do not automatically gain current qualification.

Every original Session Draft writer, including ordinary persistence, stale-Save retention and explicit recovery resolution, uses the Session's original stamped file identity and frozen scope. It never selects Draft ownership from an old path's current occupant or current library. A Server-configured namespace supplies its separate authorization check and cannot replace original file ownership.

A committed same-object relocation updates only the primary locator within the same FI and scope. Exact previous bytes enter the existing `draft-history` before that unique primary is updated. Path-hash slots and records missing scope no longer merge current proposals, and no consumed-marker/migration protocol remains. Originals are retained with explicit unsupported qualification when necessary evidence is absent. Archives supply preservation and explicit comparison only; they cannot resurrect input after discard/merge. A corrupt or unqualified primary cannot fall back to another scope or old history.

The same FI and library scope do not prove the current location after an external change. Source remains viewable after an external rename or rollback to a historical coordinate lacking the original committed placement relation, without automatically recovering, migrating or consuming the old Draft. Historical coordinates cannot impersonate current migration proof. A newly opened session retains its unconfirmed placement qualification in memory; subsequent persistence/Save explicitly refuses with `identityPending` rather than overwriting the original private record. The editor retains current input and reports recovery-Draft persistence failure. An originally qualified session can still continue writing under its original FI and placement relation after a committed move/exchange, without selecting a Draft target from another object's identity now occupying the old path.

Complete Draft records, including Base, proposal and every alternative, share a 16 MiB read/write budget. Validate complete proposed bytes before replacement. Excess input, read or persistence failure preserves the old readable Draft rather than truncating it or checking source length alone. Current scope-upgrade regressions and HTTP/browser checks bind their exact source and artifact; prior candidate results do not automatically qualify the new format. MVP retains platform and actual power-loss limits.

Windows Compound namespace acquisition captures each retained directory's original normalized handle coordinate once. Address comparisons use that fixed name projection, including short-name aliases in qualified ancestors, while current source FI, parent FI, placement phase and descendant membership remain independently required. Moves and later directory retention do not rewrite the original projection; a stale phase cannot adopt a moved handle's new address as its expected location.

### 2.5 Private capture drafts and close acknowledgements

Core retains not-yet-created input in private `capture-drafts/<draftId>.json`; it never fabricates an existing file identity for an ordinary Draft. The single v2 record starts with `scope`, fixing the local owner or server-derived actor and the exact library binding or explicit `deviceUnassigned`. Unassigned input does not belong to the currently open library. A selected library fixes its physical root identity and WorkspaceId; a parent retains its stable reference and actual container identity digest. Paths only help relocate it. Replacing a library/container at the same path cannot reuse its qualification; a legitimate same-object move resolves the original reference again. A bound capture draft does not switch to another library.

`currentInput` and immutable `pending` share one atomic record replacement. Name, title, body, location/parameter raw text and every field control's raw text use explicit UTF-16 code units, preserving lone surrogates, NUL and unfinished composition. Identifiers remain valid strings. Valid native values are optional candidates, never substitutes for every raw control; DOM validity does not prove UTF-8 representability. Author-source creation performs strict conversion, retaining original code units on failure rather than inserting replacement characters. Types/fields use stable IDs; control addresses use FieldId, value path and controlRole rather than ARIA wording. Drafts do not carry old Base, full Schema, catalogs/previews or authorization capabilities.

Record `revision` provides CAS, while `inputRevision` tracks input changes and same-value ABA separately; both remain within JavaScript's exact integer range. A mutationId and command fingerprint permit same-command recovery after the last durable write loses its reply. Read-only recovery queries carry the frozen original typed command, including its original expected revision; matching an ID alone never proves that another command was stored. Reusing an ID with another command or writing an old revision cannot overwrite newer input. A negative lookup means superseded or unknown, not proof that a write never happened. Updating a missing record cannot create it implicitly.

Field input separates private exact raw from proved personal text. `CaptureRawInput.text` is the complete current UTF-16 field value and may contain programmatic prefills or protected defaults. Only independent author.text/provenance enters the pure personal projection. Provenance binds the actual producer, inputId and observed revision, without granting authority. Unproved raw is excluded; recovered proved fragments are copyOnly and cannot reconstruct the former complete field automatically. Before a structure/Schema change retires a control, retain its original address and UTF-16 text in the same currentInput.detachedRawInputs with a retirementId and reason. Replacement list indices, union branches and same-name fields cannot inherit the binding. Live and detached raw share the 1,024-entry and record budgets, without another history ledger. After resource authorization retires, a still-authenticated actor receives only its own pure projection, excluding private complete raw, old Schema candidates, templates, private target paths and frozen wire. Pure-input updates retain scope/pending and cannot change protected fields or produce author effects.

The six top-level name/title/body/rootInput/parentInput/parametersText controls likewise separate their complete private values from authorTexts in the same record. Each slot retains proved fragments by actual producer/inputId, with at most 1,024 total entries. Only newer revisions of the same identity replace a proof; changed bytes at the same revision and revision rollback fail. A new window cannot overwrite an older producer or relabel its fragments with new provenance; empty text remains a new deletion proof for its original identity. Programmatic prefill, DOM sampling and restoration update only private values without author proof. A pure author checkpoint merges only the own overlay. A field producer change retains the old proof as detached input rather than replacing its private candidate. Freshly authorized hosted active separately returns all six complete values and body mode; a revoked pure projection cannot reconstruct a submittable body automatically.

Field structure has one valueState: valid {value: NativeValue} or incomplete {wire: CaptureText}. Incomplete holds exact JSON/UTF-16 for one private native field tree, retaining siblings, union tags and list positions beside an unfinished scalar, without Schema/Base or an entire business form. Both states reject duplicate/unknown native members. An unfinished scalar requires matching live exact raw at the same FieldId and original ValuePath. Complete trees use valid; submission accepts only valid. Restoration freshly qualifies the original FieldId, Schema identity and semantic digest. Stale/unknown addresses retain originals as unbound material without author input/proof events. The old value/null format is explicitly unsupported, without a compatibility path.

A normal authorized edit persists one atomic full input including its proved author overlay. The same record durably labels inputCut as full or authorOnly and its existing lastMutation has a closed command kind. An explicit owner-only checkpoint cannot acknowledge a complete form, freeze or dispatch a new author effect, or grant a full form close proof. Target changes and neutral checkpoints preserve that cut. Restart without a full cut exposes proved own fragments copy-only; no RAM flag or former private candidate renews form readiness. Unknown full delivery first queries its exact original mutation, expected revision and canonical full digest, without storing that candidate in browser transport or overwriting a possible success with a new pure mutation. Only a freshly authorized complete input mutation establishes full again. The digest-only reader requires the original Input command kind; another command's real digest cannot impersonate a full-input ACK. Empty own text with a newer proof remains explicit deletion evidence.

The frontend uses one Records v3 pure-input recovery store and one IndexedDB transaction-CAS backend. Capture entries isolate deployment/actual actor/real draftId/producer. One entry separates current personal UTF-16 input from an unconfirmed mutation's frozen personal cut, expectedRevision, original ID and fingerprint; an ACK for old A cannot delete newer B. It excludes Schema, defaults, templates, targets, typed candidates, private complete raw and frozen effect wire, without another Capture raw ledger. ## 5. Default local saves and backend contract

Desktop does not require a checkout for each save. The initial choice is a short exclusive content-write window on Windows local NTFS. Qualification is specific to the actual volume/filter/path; cloud placeholders, network drives and aliases are not qualified by using the same API. Existing-file content updates and directory namespace operations use different protection methods.

**Existing-file content update.** The backend obtains a read/write handle denying shared read, write and delete, and proves canonical containment, absence of reparse/uncontrolled hard-link aliases, and path/object binding. It reads complete current bytes through that same handle and compares them to Draft Base and Plan before. The handle stays open through complete after writing, flush and durable commit. This avoids closing the guard and then performing hash/rename. An external editor's existing writer yields a sharing conflict: retain Draft, retry within bounds and explain that the file is busy. External new bytes discovered after acquisition conflict rather than being overwritten.

Windows sharing modes check existing access and restrict later write/delete, including the documented writable-mapping conflict. This makes same-handle verification followed by in-place writing a testable candidate. It does not automatically prove ancestor stability, filter behavior, exclusion of new directory entries or power-loss durability; those need separate coverage. Byte-range or advisory locking alone is insufficient. [Official CreateFile documentation](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilea)

Complete in-place writing is not crash-atomic for one file: the journal first retains complete before/after images, but a crash can leave partial bytes. Core reader barriers prevent current reads of half-written content; restart checks recovery first. Ordinary external tools may see partial bytes after Core terminates, so both content and recovery journal must be retained. A replace-based backend qualifies only when exclusion remains held and actual displaced bytes are proved; read-hash-rename is not CAS.


### 5.1 Building the closure

1. Fix Workspace/volume identity, source Ref/object, source/target parents, basename and required permissions. Resolve relative paths from an authenticated volume root rather than reinterpreting a mutable DOS drive alias. Reject escapes, unknown mounts, reparse/symlink and nonunique hard-link aliases. Check directory object type as well.
2. Collect every directory chain from the trusted volume/workspace root to source, source parent and target parent. Each backend must state why location above the workspace root is stable; an old absolute string is not a root. Acquire one guard per physical directory object and reuse shared ancestors, avoiding conflicting duplicate DELETE handles.
3. Compute access from path roles first, then acquire root to leaf. A Windows directory handle needs actual `FILE_LIST_DIRECTORY` read-data access and `FILE_READ_ATTRIBUTES`, sharing `READ|WRITE` but not DELETE. The source's same guard includes DELETE on its initial open when it will be moved. Attribute-only access is not exclusion. Do not later reopen a DELETE handle conflicting with an existing no-shareDELETE guard; an access-role upgrade requires side-effect-free replanning.
4. Verify each child volume/object/type through its actual parent directory entry, then compare the child handle. Validate the complete current chain and original source binding. Use `OPEN_REPARSE_POINT` to open reparse points themselves and reject unauthorized resolution; subsequent operations use the proved parent/name. Failure to acquire a guard or mismatch releases all protection and retains Draft for bounded retry/conflict. Never release guards and then write using an old path string.
5. The target name is prospective; earlier enumeration does not prove absence. Final create/rename uses atomic create-if-absent/no-replace. A raced name conflicts with both sides preserved. Directory guards stabilize the directory itself and its ancestor location, not child creation.

Keep the complete namespace continuously guarded through actual operation, verification and durable commit. Rename through the source guard that already has DELETE, keeping target-parent guards; do not close the source and move by path. Only an already completed final source may use the protected guard handoff in §5.2. Use the actual target-parent handle for relative naming where required; a verified volume-path API may be used while the whole chain is guarded. The backend must verify this API combination separately; SQL locks establish none of it.

### 5.2 Overlap, moves and Node renames

An ordinary same-volume move is one no-replace rename of the bound directory object with unchanged basename. Earlier additions/edits travel with its actual tree; later changes are new external observations. Receipt proves placement, not frozen tree bytes or a source revision. Trash/restore similarly move the original directory to a unique batch/authorized empty target, retaining tree/bytes/restoration facts without recursive deletion.

Reject a destination parent equal to the source object or within its descendant chain. A source/target at the actual same location is a qualified no-op; an identically named different object is not. Shared parents use one guard. Cross-volume moves use explicit copy plus conditional Trash, not same-object rename.

Node `A/A.typ→B/B.typ` remains two steps. Record exact directory/canonical-leaf objects, names and recovery responsibility. After no-replace leaf rename, close the leaf handle if it prevents outer rename, retaining the directory guard and complete ancestor/target-parent closure. After outer rename, reacquire the actual canonical file guard and validate object/control role and declared external changes. New leaf/root third states are pending, never overwrite rollback targets. This leaf-release window gives no lasting old-source write qualification and claims no frozen tree content.

On Windows, a same-directory leaf rename uses the original file handle, a simple basename and `FILE_RENAME_INFORMATION.RootDirectory = NULL`. Passing the already retained DELETE source-directory guard as a relative target would cause a sharing conflict when Windows internally reopens that directory. Cross-directory moves still use the retained actual target-parent handle, preserving the full directory closure and no-replace guarantee. See the [Windows rename contract](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information).

A Compound root that has reached its original final position and will serve as another participant's target parent no longer needs DELETE access. Before reopening its members, open its original canonical leaf through the retained source handle with ordinary READ/share0 and verify the leaf identity. Keep that leaf and every ancestor/target-parent guard while closing the source DELETE handle. Reopen the directory through its retained actual final-parent handle and final basename, with LIST_DIRECTORY/READ_ATTRIBUTES and READ|WRITE sharing without DELETE; verify the original directory identity and install the guard under its capture-time key before releasing the leaf. The open canonical file prevents parent rename during this handoff. Missing/busy/foreign witnesses or failed directory reacquisition stop the original operation with no subsequent writes, preserving its pending Plan. Before/leaf-renamed/parked roots retain DELETE. Recovery performs the same handoff for already-final roots before capturing their files, including a final parent whose child is still parked. Subsequent membership, file identity and before/after content checks remain required.

Continuing a descendant's history or Query identity also requires exact member-placement evidence in the original Relocate. Select relevant members from existing birth/directory-admission facts and record their relative positions, stable IDs, physical file/directory objects and parent objects, without scanning private source or creating another placement ledger. This evidence does not add whole-tree byte CAS to ordinary moves; legitimate late edits and additions still travel with the original tree. Execution and original-operation recovery must verify member objects before recognizing their placement continuation. A legacy ancestor-move record containing only path prefixes cannot prove that a descendant traveled with it. A former descendant cannot borrow a move of another object occupying the old address; unproved identity remains explicitly pending.

Ordinary source save also uses its parent/ancestor closure plus an RW share0 file guard, checking Base and writing/flushing/committing through one handle. Guarded ancestor/target-parent changes cannot redirect the write after its last check. Busy retains Draft. The guard set is finite, not a workspace-wide lock.

Installation:

1. After the journal and exact blobs are durable, acquire §5.1 target ancestors/parents and Core scope reader barriers. Reserve simultaneous handle capacity for all planned files before installation. Insufficient capacity fails or produces an explicit revised batch plan before writing anything.
2. Create each new planned directory and obtain its original guard in one backend call, not `mkdir → reopen`. ### 5.4 Purge: fixed confirmed objects and actual empty-directory deletion

Purge remains authorized and destructive. Fix the root, confirmed bytes/membership and reject known ignored/unmanaged boundaries first. An ordinary local tree has no exclusion of raw additions; use preservation rather than naming a folder controlled staging:

2. After durable installing, set disposition on exact file handles and flush/close as required. Do not recursively delete mutable paths. Journal actual deletions and original-ID recovery responsibility. Retain necessary before data until commit; half-deletion is not success.
3. Delete original confirmed directories bottom-up with handle-based `delete-if-empty`. New raw children make the OS return directory-not-empty and remain in the actual Trash tree. Unknown children never enter the deletion set. Guards stabilize the directory; the deletion primitive performs atomic emptiness checking rather than `list empty→recursive delete`.
4. Commit successful purge only after every originally requested directory has been removed and tombstones/responsibility are complete. Nonempty/busy returns pending_reconciliation with exact processed objects and real residual content under the original operation ID, never whole-tree cleared. Recovery only resumes the original explicit set or recreates provable objects no-replace. Unknown residuals are never deleted or overwritten.

A quiescent normal local Trash can finish purge; concurrent new drafts survive for an explicit decision. No exclusive whole-namespace guarantee follows. Deployments needing atomic whole-tree erase or strong business negative scopes use an independently permissioned/fenced Server writer, not same-user ACL naming.

Known ignored/unmanaged boundaries reject the action without re-entering them. A late boundary discovered after rename but before commit retains the actual tree as pending, never overwriting a third object at the old path. A new boundary after commit is a later external observation; it cannot revoke the original historical Receipt or execute the move again. Absolute absence of boundaries/unique values under arbitrary raw additions is a strong negative-scope contract, not proved by local directory guards. Ordinary same-object moves, fixed-snapshot copies and safe purges have their own precise completion conditions instead of all becoming unavailable.

The root's administrator-owned parent prevents ordinary clients/workers from replacing its root entry. File synchronization and directory-entry synchronization are separate durability steps. Source/read scopes retain compatible in-process leases under the already isolated service authority. The hosted compiler broker binds to the same retained `ValidatedEnrollment` as the admitted Core backend. Its original path, identity and complete enrollment digest remain pinned across launches; separately re-reading a pathname cannot substitute authority. One per-instance launch permit remains with accepted work through its original child-tree receipt when an HTTP caller disconnects. Network filesystems require individual qualification. Optional checkout and three-way return serve long external editing or unqualified backends, preserving original Base/current/proposed; checkout is not mandatory for normal Desktop saves.

The contract need not resist a disk owner deliberately bypassing isolation, damaging journals or a malicious kernel. Ordinary editor/sync races, existing handles and mappings are within the validation scope. Out-of-scope behavior does not justify claiming safety against arbitrary external writes. Without required protection, retain the draft and return the actual operation boundary; never silently downgrade to an observed-only save that may overwrite an unseen draft.

## 6. Executable commit and recovery algorithm

1. Read the original operation/canonical Intent fingerprint. Same ID/request resumes/replays; changed input conflicts. Durably retain the fixed Plan, actual objects, recovery responsibility, needed before/after blobs and budgets. Draft retention is not saved.
2. Acquire §5 directory closure, file guards and scoped Core reader barriers. Validate binding, authorization, schema, lifecycle and actual dependencies. Failure preserves Draft for bounded no-change retry. No rename occurs here. Ordinary moves do not freeze child bytes; copy fixes snapshot members, purge fixes confirmed objects, strong business actions require complete scopes.

#### 9.1.1 Sole producer and opening algorithm

The Core commit marker atomically advances one journal generation with every admitted source/config/lifecycle/placement fact of that generation. A multi-object transaction has one generation. 1. Verify the caller's current potential scope and minimum disclosure. Acquire a short commit/read barrier and wait for relevant Core installations to become committed or explicitly unavailable; never read half-installed state.
2.
