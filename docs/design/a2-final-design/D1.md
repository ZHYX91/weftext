# A2 D1 Product Surfaces, Capability Boundary, and Release Evidence

Status: current A2 candidate for D1 in the first integration batch.

## 1. Authority and current decision

D1 owns product surfaces, execution modes, capability ownership, process/trust/network boundaries, state ownership, and release/evidence sequencing. D2-D10 own their domain protocols.

The current D1 decision combines the fixed-S surface/release contract with the later file-authority afterimage. The material changes are explicit: one logical Workspace may have several registered physical replicas; each physical replica has at most one durable local commit holder; a hosted backend has at most one durable Server commit holder across processes and failover overlap; Server may have many user sessions; and global execution responsibility is separate from ordinary content replicas.

No database, sync provider, worker, Agent, automation engine, connector, cache, or UI becomes a second author-write authority.

## 2. Formal product surfaces

### 2.1 Desktop

Desktop is the complete local file-workspace surface and an optional Server client. It owns device UI state, file authorization, Drafts, selection, accessibility and interaction state. Local mode calls local Core; remote mode calls Server. The WebView never writes workspace files, portable metadata, durable control, or derived index directly.

### 2.2 WebUI

WebUI is always a Server client. Browser storage may retain an explicitly uncommitted Draft or cache, but it is never hosted workspace authority and never opens a local workspace directory as the product write boundary.

### 2.3 Server

Server owns hosted authentication, authorization enforcement, audit, hosted backup/recovery, client APIs and multi-session coordination, while invoking the same Core semantics. Multiple users may concurrently read, hold Drafts, prepare, or edit the same or different documents. Durable commits serialize only on actual write/dependency requirements. A stale Base never overwrites a newer source.

### 2.4 CLI

CLI supports local and remote modes with the same Core results. Destructive, external, conflict-resolution, or approval-sensitive operations require explicit inputs and cannot hide confirmation.

### 2.5 Mobile

Mobile is a formal independent surface, not a WebUI wrapper. Local mode may write only when the platform backend proves the required installation/durability contract; otherwise the capability is explicitly unavailable. Remote mode is a Server client. Conversion execution, Agent sessions, automation scheduling, and connector credential/run management remain outside the current Mobile boundary; Mobile may consume already committed connector results where the capability matrix permits.

## 3. Global invariants

1. One physical local replica has at most one durable commit holder at a time. One hosted backend likewise has one durable commit holder across Server processes, instances and restart overlap.
2. Different registered physical replicas may independently perform ordinary offline content commits. This is not global execution-authority duplication.
3. Desktop, WebUI, Server, CLI and Mobile share Core domain results, diagnostics, plans and commit semantics.
4. WebUI never becomes a local-file author boundary.
5. Desktop, CLI and Mobile remote mode never reinterpret remote results with local Core/cache state.
6. File sync transports ordinary files and portable metadata only. External change invalidates only the qualifications that depend on affected observations/ranges; it does not turn the whole Workspace permanently read-only.
7. Workers, Agents, automation and connectors produce inputs/results/proposals only; author commits still pass Core or Server Core.
8. Capability state is versioned product state, not button visibility, OS guessing, cached history or a prior success.
9. Unsupported, undelivered, unconfigured, offline, incompatible, unauthorized or policy-denied cases never fall back to approximate writes.
10. Platform support claims require real build/install/launch/scenario evidence.
11. Public artifacts have no production platform signing/notarization/store identity in this design; development signing is not a release capability.
12. Product state distinguishes retained input, not saved, reliable, durable observed-only, recovery unknown, and portable-publication pending/published. Observed-only is limited to the existing D6 trusted-interactive single-live-Document ordinary whole-source save path.

### 4.3 Mobile delegation and exclusions

Mobile executes the same domain semantics but may delegate hosted work to Server. It does not gain conversion-worker execution, Agent execution, automation scheduling, or connector credential authority through delegation. A hidden or unavailable button never changes these boundaries.

## 5. Execution modes, concurrency, and custody

### 5.1 Local replicas and ordinary synchronization

Each registered physical replica has its own replica epoch and local commit domain. Desktop/CLI/Mobile processes on the same physical replica must contend for one durable commit qualification. Different replicas may both edit offline.

File sync is transport, not collaboration. Partial arrival, placeholders, source-before-metadata, metadata-before-source, concurrent content, structure, lifecycle or policy heads must be surfaced through current D3/D6 completeness/conflict rules. No mtime, path, filename, digest, last uploader or arrival order is an automatic winner.

An external change invalidates only dependent SourceObservation/cut/install ranges. After requalification, unrelated documents and operations continue. Observed-only never overwrites an observed competitor.

### 5.2 Server multi-session behavior

The hosted backend has one durable commit holder, not one user. Same-document non-real-time concurrent edits are allowed as Drafts. If A saves from r5 to r6 first, B's r5 Base becomes stale/conflicted; B retains the Draft and the comparison. Different-document reads/preparations may run concurrently and commits serialize only on real dependencies.

Failover must fence both control storage and author-file writes. Fencing only SQL while an old instance can still rename/replace files is non-conforming.

### 5.3 Execution custody is a separate domain

Approval-use counts, Money, external-unknown responsibilities, Automation execution and stop responsibility require a continuous fenced execution-responsibility domain. Copying workspace files or portable metadata never copies these consumable responsibilities. A replica without execution custody may still edit ordinary content.

### 5.4 User-visible state milestones

The surfaces distinguish T_first_open, T_first_edit, input retained, T_first_reliable_save, durable_observed_only, recovery_unknown, portable publication pending/published, T_full_search_ready and T_OCR_ready.

Preview, Prepared, Draft persistence, HTTP success, sync upload, worker success or planned durable control state is never file-save success. Observed-only latency is not counted as T_first_reliable_save.

## 6. Trust, authorization, disclosure, and indexes

Authorization is revalidated at the boundary holding the backend. Client claims, sync-provider state and index completeness are not authorization evidence.

Ordinary operations read only the source/identity/structure/policy ranges they actually need. Strong Actions must prove their complete positive and negative ranges under the relevant downstream owner. A partial index is a candidate accelerator only; inability to prove a complete range blocks that strong operation, not unrelated ordinary save.

Policy denial masks component/configuration/network/version/temporary-health detail. Revocation and commit are linearized by the authority-holding boundary. One participant cannot donate authority to another participant's input.

## 7. Capability negotiation and unavailable semantics

### 7.1 Stable major negotiation and read-only compatibility

Before any workspace read, capability description or commit, peers exchange supported contract-major sets through a stable read-only bootstrap semantic and choose a common major. With no common major, the only bootstrap outcome is incompatible_version plus both supported-major sets.

After a major is selected, an unknown capability ID is unsupported_feature. Client/Server major mismatch rejects both reads and writes unless the release manifest explicitly approves that exact combination for read-only interoperability; a client cannot infer compatibility because a payload “looks readable”. Optional worker/provider version mismatch affects only the capability that consumes it.

### 7.2 Closed unavailable reasons

The only capability states are available and unavailable. unavailable has exactly these reasons:

| Priority | Reason | Meaning |
| ---: | --- | --- |
| 1 | unsupported_feature | capability ID is not in the selected major |
| 2 | unsupported_surface | known capability is prohibited on this surface |
| 3 | not_in_release | product direction exists but this coordinated release does not deliver it |
| 4 | policy_denied | principal/deployment policy refuses it and masks later deployment detail |
| 5 | user_action_required | an explicit local/network/device permission must be granted by the user |
| 6 | missing_component | required optional component is absent or removed |
| 7 | not_configured | delivered component exists but is not configured |
| 8 | offline | required local/network carrier boundary cannot be reached |
| 9 | incompatible_version | reachable boundary has a disallowed caller/Server/worker/provider version combination |
| 10 | temporarily_unavailable | boundary/configuration/version are valid but the internal capability is transiently failing |

### 7.3 Priority, masking, retry, and repair

Exactly one reason is returned: the first true row above. Static product/release data decides rows 1–3. policy_denied is evaluated before probing component/config/network/version/health details and stops their disclosure. offline and temporarily_unavailable are mutually exclusive by whether the carrier boundary is reachable.

A capability result also supplies the capability ID, retryability and a non-secret repair category. Probe success is never an authorization ticket; actual operations revalidate policy, backend qualification, observations, frontier and dependencies. A strict request never silently downgrades to observed-only.

Workspace-busy, stale-revision and target-conflict outcomes are operation errors owned downstream and are not new D1 unavailable reasons.

## 8. Release claims and evidence

### 8.1 G1, G1.1, and G2 artifacts

| Stage | OS / CPU | Artifact | Claim | Explicitly not claimed |
| --- | --- | --- | --- | --- |
| G1 | Windows 11 x86_64 | unsigned NSIS Desktop exe plus x86_64 ZIP CLI | listed local Desktop/CLI capability rows | Windows ARM64, macOS/Linux Desktop, Server/WebUI, Mobile, conversion, Agent, collaboration |
| G1.1 | Ubuntu 24.04 LTS x86_64 | tar.gz CLI | listed local headless workspace capability rows | Linux GUI, other distro/CPU, Server |
| G2 | Ubuntu 24.04 LTS x86_64 | Server + embedded WebUI tar.gz; optional same-content OCI image tar | authenticated hosted workspace, WebUI, backup/recovery, listed API rows | other Linux/CPU, hosted SaaS, real-time collaborative text unless separately evidenced |

WebUI is delivered with Server, not as a local-file download. Mobile remains a formal product surface, but this contract does not claim an ordinary-user iOS/Android production package.

### 8.2 Evidence required for every Supported row

A Supported row requires all of the following for the exact artifact:

1. native OS/CPU clean-runner build from exact tag/commit, locked toolchain and lockfiles;
2. machine manifest containing artifact name/version/target triple/byte length/SHA-256/SBOM/licenses/NOTICE/known limitations;
3. clean machine install or extraction without source/development tools, launch, minimal end-to-end scenario, restart, uninstall/cleanup, and platform-native digest verification instructions;
4. automated package smoke plus independent human clean-install evidence tied to the same digest;
5. GUI evidence for keyboard, IME, scaling/high contrast and actual platform warnings; Server evidence for persistent volumes, authentication, backup/restore and tested browser versions;
6. runtime capability description matching package contents;
7. missing/failing evidence moves the row to Experimental/Unsupported; another platform's Core tests never substitute.

### 8.3 No production signing, warnings, integrity, and rollback

Public release artifacts in this design do not claim production publisher signing/notarization/store identity. Debug/development signing or provisioning required by SDKs, CI, simulators or registered test devices is permitted only for development evidence; it never enters public GitHub Release or Supported claims.

The release first screen states Included, Not in this release, and How to verify. Windows instructions record the actual warning and continue/cancel path and never tell the user to disable SmartScreen or ignore a digest mismatch.

G1 does not promise silent installation, automatic update or background elevation. Manual update, visible rollback instructions and workspace-backup steps are required. Supply-chain provenance may supplement SHA-256 verification but is not production publisher identity.

### 8.4 Dependency graph

After shared Core, G1 ships first. G1.1 CLI evidence and Server security foundation proceed in parallel after G1; G1.1 does not block G2. Server security -> WebUI -> G2. Real-time collaboration follows G2 and does not block a safe non-real-time hosted release.

Mobile local implementation depends on shared Core + D8 mobile interaction, not Server; Mobile remote depends on stable Server API. Conversion depends on D9 and does not block basic G1/G2. Agent/automation/connectors depend on reusable Action/permission/audit boundaries and do not block basic surfaces.

## 9. Large-workspace behavior

Opening, editing and saving an active document must not require complete metadata, full search or OCR. Implementation uses progressive, bounded and resumable derived indexing. Complete Actions either prove full coverage by scan/current qualified index plus reread or explicitly refuse. No seconds-level performance claim is made without measured evidence.

## 10. Real-time collaboration boundary

Real-time collaboration is post-G2. Its future interface must separate participant/session epoch, input sequence/Base, IME preedit/final input, transient broadcast and durable checkpoint, and must handle revocation/disconnect/reconnect/gap reset. The collaboration algorithm supplies one managed source proposal to Core; OT/CRDT choice is not frozen here and no collaboration log becomes author source.

## 12. Implementation and acceptance obligations

### 12.1 Fixed-S implementation-impact tests

The fixed-S D1 Implementation Impact contributes all thirteen source-qualified tests:

1. Core has no UI/Server/worker/Agent/provider/network dependency and surfaces contain no prohibited direct path.
2. local Desktop/CLI/process contention has one commit holder.
3. dual Server overlap/failover has one hosted commit holder.
4. external/partial sync change invalidates old unsafe qualification without silent merge.
5. startup major negotiation fails closed before capability/workspace reads.
6. unavailable reasons obey the ten-row normalization/masking order.
7. the same fixture has equivalent canonical results across all five surfaces.
8. remote clients never locally interpret/commit hosted workspaces and browser never gets hosted paths.
9. worker/broker has no writable workspace mount or second submit authority.
10. every Supported artifact has build/hash/SBOM/license/smoke/clean-install/warning evidence.
11. public artifacts make no production-signing claim and development-signed Mobile artifacts are not public support rows.
12. public prose contains no unsupported cross-platform/Mobile-production/sync-as-collaboration/local-WebUI/signed/conversion-or-Agent-built-in claims.
13. retirement search rejects obsolete prototype names, aliases, fallbacks, dual paths and bridges.

### 12.2 Current-owner afterimage acceptance

The later owner adds current tests for registered replicas, range-scoped invalidation, Server same/different-document sessions, revocation/reconnect/restart/failover, partial-sync/placeholder handling, separate first-open/edit/reliable-save/search/OCR measurements, no-body-replica P/I, and explicit not-in-release collaboration.

Its implementation-impact negative matrix also requires: move/edit and Trash/edit conflict, portable metadata not duplicating Approval/Money, I deletion not losing authority facts, P loss not reconstructing external unknown/receipts/Money, DB-only failover fencing to fail, partial index not proving complete Action, automated Draft/background/reconnect never initiating observed-only, narrow permission never becoming whole-source permission, observed competition becoming stale/conflict, and observed-only being forbidden for strong/bulk/D3 structural/Automation/approval/Money operations.
