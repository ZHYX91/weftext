# Typst Core: files, commits and operating boundaries

Status: an author proposal selecting technology again from requirements; not accepted or implemented. Fixed input commit: `d167ae8c1d0346faf62e8e0887cf789de0bf0b89`. The [requirements](../typst-native/REQUIREMENTS.md) are authoritative; this document and this set's [SOURCE](SOURCE.md), [EDITOR](EDITOR.md) and [FEATURES](FEATURES.md) define one new design. Earlier protocols and bounded reviews remain historical evidence, not dependencies of this contract. Product, crash, power-loss, synchronization, Server, security and performance acceptance have not passed.

## 1. One file workspace and one author commit path

Weftext's native Rust Core serves Desktop, CLI, Server, WebUI and future Mobile. Local Desktop/CLI call local Core; their remote modes and WebUI call Server only. Offline hosted clients may retain Drafts but cannot grant themselves hosted commit eligibility. Mobile local writes require a qualified platform backend. Real-time collaboration remains later work; future OT/CRDT also submits an explicit author proposal.

Ordinary saves, field edits, creation, moves, copies, Trash, restoration, annotation suggestions, templates and business actions all use Core `Intent → Plan → OperationJournal → Receipt`. UI, converters, agents, synchronization and indexes have no second author write entry. Conversion and external execution use recoverable Jobs; a Job's workspace changes still enter the same Plan.

Persistent writes are ordered by actual conflict scopes. Multiple users may read, edit, retain Drafts and prepare concurrently. A physical replica's final durable commit coordinator may serialize briefly; this does not mean prolonged workspace-wide blocking or a single user. Different replicas may commit ordinary content offline without duplicating external execution responsibility.

## 2. Sole file and structure authority

A managed Node is `X/X.typ`. Its body, declaration, fields and author styling reside in that Typst source. SOURCE's explicit author roles define title and subtitle; no title is valid, and filename is only a display fallback. Resources are ordinary files; independent annotations use `weftext.annotations.json`. There is no second body or shared presentation database.

The exact root `.weftext-format` bytes are `weftext.typst.v1\n`. One `.weftext-workspace.json` records WorkspaceId, current schema and storage-contract selection. The marker selects a format; it grants no identity, permission or historical continuity. Directories without a valid contract are unmanaged, incompatible or incomplete as appropriate; no format guessing or automatic conversion occurs.

The directory tree is the only parent/name/path authority for live Nodes. Portable metadata does not maintain independently editable parent/children lists. A parent's sorting policy and a child's sparse manual rank record ordering that the tree does not express; natural name order is the default. The actual Trash directory tree defines its internal structure. A Trash record may retain the original location, batch and restoration membership because these are historical and restoration facts; they cannot override the live tree. An occupied restoration target conflicts rather than being overwritten.

`.weftext-rules` explicitly classifies ignored, visible unmanaged and managed boundaries; it does not inherit `.gitignore`. An unmanaged directory is a complete subtree boundary that scanning cannot re-enter. Ignored bytes remain backup content. A canonical `.typ` cannot be classified separately as unmanaged. Core alone produces inventory for all shells and Query. Structural changes reject targets inside ignored/unmanaged boundaries and managed subtrees with a known such boundary. Strict exclusion of unobserved additions in an open tree requires strong scope capability; §5 retains late-boundary pending handling rather than presenting scanning as CAS.

Managed directories provide stable shortcut targets. Node directories use NodeRef. Core `admitDirectory` creates `weftext.directory.json` for a non-Node container, recording only DirectoryId without duplicating parent/name/path. Creation, fresh copied IDs, moves, duplicate IDs and gaps use the same Plan/manifest rules. Creating a shortcut admits only its selected container, not the entire library. Unmanaged boundaries receive no automatic ID. If kept unmanaged, an explicitly weaker locator bookmark is possible but is not a rename-stable shortcut. Root `.weftext-tags.json` registers immutable TagId and mutable displayName; TagRef supports stable shortcuts, navigation and Query. Equal names do not merge automatically, and literal label strings do not register objects. Core `createTag` may accompany a note's typed TagRef assignment in one Plan; SOURCE owns the native typed slot.

Portable control data records only facts current files cannot recover: identity creation and retirement, schema history, committed versions and causality, resource-file bindings and Trash restoration information. A resource's stable Ref binds its resource ID to a relative file locator in node-local `weftext.resources.json`; that file does not determine Node parentage. Ordinary noncanonical files remain visible. Unregistered resources do not automatically receive stable IDs. A raw rename without proof of the original object requires explicit rebinding or conflict resolution. Annotation IDs in JSON are separate from their targets and lifecycle.

`.weftext-history/` retains immutable committed manifests and required exact blobs. It supplies history, replication and recovery evidence; it cannot be edited into another current source. Device/session Drafts, active SQLite journal/WAL, runtime credentials and derived indexes reside outside the synchronization root. Between durable commit and manifest publication, the original journal's committed record and complete blobs provide actual evidence of this operation's identities/revisions/results. Startup recovers pending publication first, and backup consistently includes these records; missing history cannot trigger execution again. A historical snapshot can differ from current files; current reads still observe actual files and current authorization. Indexes, search, reverse relations, thumbnails and graphs are rebuildable; rebuilding cannot restore missing execution responsibility or invent IDs.

A complete backup includes ordinary files, ignored bytes, portable control/history and consistently captured local unresolved journals/Drafts. Copying an active SQLite main file alone is insufficient. A content-only backup may be exported separately, with an explicit limitation that it cannot recover missing operation or financial responsibility. Restore on another device creates new local observations and derived indexes. Actual pending execution responsibility comes only from its original journal or an explicit custody transfer.

## 3. Identity, revisions and current reads

Random UUIDv4 remains the identity choice. WorkspaceId and Node/Resource/Annotation/Directory/Tag IDs form fully typed `EntityRef`s, supporting rename-stable references, offline creation and independent copied identities without making names or paths identities. A UUID is a stable random identifier, not a security credential. Directory/Tag add only identity required by navigation; they are neither notes nor per-value fact IDs. Core allocates new identities; source/sidecar IDs are claims. An existing identity must match admitted creation evidence, its current unique file binding and lifecycle. Duplicate IDs, external copies carrying IDs, missing metadata and partial synchronization do not create identities or trigger new IDs automatically.

Workspace creation constructs the complete root configuration, schema, empty history and all target bytes in private staging, then verifies absence and publishes create-only. Initialization failures do not activate a prefix. Server creator permissions arise solely from an authorized administrative service action; client metadata grants none. Existing directories use explicit import/admission, preserving originals, unknown bytes and losses rather than importing by extension rename.

`RevisionId` is a random identifier privately allocated when freezing a Plan. It becomes valid only at commit. The manifest binds EntityRef, RevisionId, exact blob, causal parent revisions and transaction once. It does not depend on a digest of source containing itself, so final `.typ` can hold self/cross fixed addresses and annotation anchors. Private planned IDs are not published success. A true no-op retains its revision; equal-byte external admission is a new provenance-admission fact.

`ReadBasis` is this Core instance's current qualification: persistent revision or explicit external observation, observer incarnation, actual file object and change generation, lifecycle, schema/authorization generations and actual dependencies. Hashes verify byte integrity, not object identity, authorization or conditional writes. Watcher gaps, restart, replacement, ABA, partial materialization and relevant dependency changes invalidate old bases. A new read after rebuilding may acquire a new basis; it cannot revive an old plan or selector's write eligibility.

`DependencySet` has one family of typed object, lifecycle, structure/range, schema, authorization, environment and World-read dependencies. Complete negative ranges and absence require current authorized enumeration. Placeholders, I/O errors, hidden objects and unfinished indexes do not mean absence. Unrelated object changes do not invalidate a save depending only on this document. Strong actions requiring complete scopes or constraints must prove their actual scope; ordinary save success proves no workspace-wide completeness.

Authorized raw reads may retain valid or invalid external bytes. Unadmitted external state has no persistent typed write address. An ordinary whole-source save may check that same external Base within a short protected window and explicitly admit it without first compiling the entire body. Save semantics separately report local_valid / semantic_pending. Unproved cross-object conditions cannot be downgraded into successful strong actions.

## 4. Frozen plans and exact results

`prepare` receives operationId, typed Intent, Draft Base and budget. Core authorizes the actual potential scope before reading. The Plan retains actual read/write sets, complete before images, exact after blobs, identity/revision allocation, structure capture paths, constraints, actual transforms, schema and the permitted user preview. Caller offsets, IDs, authorization flags or digests are not proof.

SOURCE produces narrow edits from the official AST and original bytes. EDITOR owns Draft sequence, selection, Undo and the safe writable subset. FEATURES owns Query, copy/template transfer and business postconditions. Core materializes every target with one map, reparses the complete after sources, and validates every actual typed reference, fixed revision, annotation range and preview match. Generated content being readable/queryable does not give it a writable address. An unanalyzable transfer preserves content and explicitly reports unavailable transfer semantics; it does not replace strings in unknown code.

One object-key-to-final-EntityRef map covers fresh/copied/existing objects; each item states disposition, source and owner. Three different result arrays are unnecessary. An independent actual change set lists genuinely changed source, structure, lifecycle, annotations and schema. Mapping an existing object does not prove a new revision. A fresh object's before is absent; a missing field in an existing Node does not make that Node absent.

operationId is unique within the workspace's current operation-origin domain, with its complete canonical Intent fingerprint fixed. The same ID and request returns original status/result; changing input under the same ID conflicts. Preparation/staging is not saved. Planning failures retain Draft. A revised proposal uses a new operation linked to the original Draft, so retry cannot silently change source, targets or allocations.

## 5. Default local saves and backend contract

Desktop does not require a checkout for each save. The initial choice is a short exclusive content-write window on Windows local NTFS. Qualification is specific to the actual volume/filter/path; cloud placeholders, network drives and aliases are not qualified by using the same API. Existing-file content updates and directory namespace operations use different protection methods.

**Existing-file content update.** The backend obtains a read/write handle denying shared read, write and delete, and proves canonical containment, absence of reparse/uncontrolled hard-link aliases, and path/object binding. It reads complete current bytes through that same handle and compares them to Draft Base and Plan before. The handle stays open through complete after writing, flush and durable commit. This avoids closing the guard and then performing hash/rename. An external editor's existing writer yields a sharing conflict: retain Draft, retry within bounds and explain that the file is busy. External new bytes discovered after acquisition conflict rather than being overwritten.

Windows sharing modes check existing access and restrict later write/delete, including the documented writable-mapping conflict. This makes same-handle verification followed by in-place writing a testable candidate. It does not automatically prove ancestor stability, filter behavior, exclusion of new directory entries or power-loss durability; those need separate coverage. Byte-range or advisory locking alone is insufficient. [Official CreateFile documentation](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilea)

Complete in-place writing is not crash-atomic for one file: the journal first retains complete before/after images, but a crash can leave partial bytes. Core reader barriers prevent current reads of half-written content; restart checks recovery first. Ordinary external tools may see partial bytes after Core terminates, so both content and recovery journal must be retained. A replace-based backend qualifies only when exclusion remains held and actual displaced bytes are proved; read-hash-rename is not CAS.

**Ordinary same-volume move.** The default means moving the bound directory object to a specified parent with its basename unchanged, not copying a frozen whole tree. Core authorizes the Ref, actual source/parent objects and boundaries. It holds a DELETE-capable directory handle allowing read/write sharing but denying delete sharing. Durable installing first records the operation, source/destination objects, locators, no-replace and recovery responsibility. One same-handle rename follows. Occupied destinations fail without replacement. Busy retains Draft and retries within bounds without changes; no prolonged child-wide lock or full-tree copying. The same directory and its tree at rename are moved. Earlier child additions and external edits travel with it rather than disappearing. Later content updates are independent external observations.

The Receipt proves placement, not fixed whole-tree bytes. Source RevisionIds remain unchanged or require separate external admission; path dependencies and current ReadBasis are reacquired. Sync cannot overwrite newer body bytes with a placement operation's older blobs. Moving an exact unchanged tree snapshot is a separate strong Intent. Ordinary move has an implementable same-object meaning without arbitrary whole-directory CAS.

**Node rename.** `A/A.typ → B/B.typ` is two no-replace steps: rename the canonical leaf by its handle, close the leaf handle if it blocks parent rename, rename the outer directory through its still-protected handle, then rebind and verify canonical role and actual objects. Before any side effect, durably record both objects, old/new names, steps and rollback responsibility. A Core barrier hides intermediate state. ID/body bytes do not change or mint a source revision. Recreated old leaves, replaced target leaves, occupied outer destinations or uncertain ownership enter pending_reconciliation, retaining real drafts/paths. Return only the original object no-replace to a still-empty old location. B/B.typ existence or equal bytes cannot manufacture saved status. The two renames are not atomic to external tools.

**Trash, restore and purge.** Trash/restore move the same directory object to a unique operation directory/authorized empty target, preserving its tree and bytes while recording batch/restoration metadata with the journal. Concurrent content remains in the actual tree. Purge is destructive and strong: in Core-controlled Trash staging, prove a complete closed membership set, necessary handles and boundaries/responsibility before deleting exact objects. Unknown additions, outstanding writers or unproved completeness pause purge; no unrestricted recursive delete. This does not disable ordinary move/Trash.

**Copy, template and cross-volume moves.** Copy selects explicit snapshot members and exact authorized blobs, allocates fresh IDs with one map and validates references while leaving source untouched. Construct the entire target in genuinely host-controlled staging outside ordinary sync/edit paths, publish no-replace, and verify ownership; a private name is not isolation proof. Later source additions/edits are neither deleted nor reported copied. A requested complete-tree snapshot without proved membership retains the proposal/pending reconciliation rather than silently copying a subset. Templates fix all finite outputs and journal every root publication/rollback without replacing third targets. Cross-volume move first snapshot-copies; source moves to Trash only when complete membership and change qualification match. Otherwise report copy completed/move pending, preserving both trees and new drafts.

Known ignored/unmanaged boundaries reject the action before modification; scans never re-enter them. A late boundary found before rename rejects it; one found afterward causes pending_reconciliation with the real tree retained, safely returned no-replace or explicitly retained at its current location. Never overwrite a third-party object at the old path. Scanning cannot claim exclusion of arbitrary unobserved additions. An absolute requirement that no unknown boundary/sibling/unique value exists at the rename instant is a strong negative-scope contract requiring controlled namespaces. Ordinary move's same-object contract is selected; platform directory durability/crash qualification awaits testing, rather than leaving all ordinary moves permanently P0 by imposing a whole-tree snapshot promise.

A bounded Windows probe verified same-object no-replace move, earlier child additions/external edits preserved with the tree, successful retry after a busy child closed, occupied destinations preserving both sides, successful Node leaf/outer steps, and failed no-replace rollback after recreation of the old leaf while both drafts survived. Even a shareALL child blocked parent rename with error 5 in this sample; closing it allowed success. Directory share=0 does not block child additions and blocks separate enumeration. The Node path therefore uses a directory handle sharing read/write while denying delete. The probe does not prove power-loss, complete recovery, generations, aliases, filters or Server behavior.

**Server and later platforms.** A Server writer service owns an OS-isolated directory; ordinary clients and workers cannot write it directly. It fences every actual file action and journal decision. This deployment can provide strong namespaces and automatic recovery. Ordinary Linux advisory locks cannot stop arbitrary tools of the same user. The initial Linux backend can support a controlled service directory or an explicitly exclusive host mode; an open local write backend requires separate proof. Network filesystems require individual qualification. Optional checkout and three-way return serve long external editing or unqualified backends, preserving original Base/current/proposed; checkout is not mandatory for normal Desktop saves.

The contract need not resist a disk owner deliberately bypassing isolation, damaging journals or a malicious kernel. Ordinary editor/sync races, existing handles and mappings are within the validation scope. Out-of-scope behavior does not justify claiming safety against arbitrary external writes. Without required protection, retain the draft and return the actual operation boundary; never silently downgrade to an observed-only save that may overwrite an unseen draft.

## 6. Executable commit and recovery algorithm

1. Read the original operation record. If committed, deliver only its original Receipt under current disclosure rights; reject a changed fingerprint under the same ID. For a new plan, durably stage exact before/after images, allocations and finite budget counters. Retain Draft before destructive writes.
2. Acquire file protection that does not change the author namespace and Core reader barriers in a fixed order. If busy, release acquired protection, retain staging and retry within bounds. Reread real objects under protection and revalidate actual dependencies, schema, lifecycle and current authorization. A change means conflict/reprepare, not resampling a replacement for the frozen Plan. Structure only acquires directory-object qualification here; no rename occurs. Ordinary move does not freeze child bytes; copy/strong actions meet their own snapshot/complete-scope requirements.
3. Atomically persist and flush the complete frozen Plan and `installing` decision in the active journal. All before/after blobs must already be durable. Record actual objects, capture paths and installation steps. SQLite proves this journal decision, not installation of external files.
4. Write content or perform §5 same-object namespace steps under protection, always after durable installing. Copy/template publishes frozen after state; ordinary move does not become copy. Verify actual objects, lengths and exact bytes at each step, and meet backend durability requirements for files and directory entries. Recorded step completion does not replace current ownership proof. I/O errors, disk-full, cancellation or revocation stop new steps and enter the original operation's recovery responsibility, retaining before/after and actual third states.
5. After checking every after image within the same Core barrier, proving the original Intent's actual result (move: same directory at target; rename: both canonical steps; copy: all selected snapshot outputs; strong actions: complete scope), and checking current authorization and necessary strong dependencies, perform one durable journal commit fixing the transaction, valid RevisionIds, full Receipt, Job author step and pending manifest. This marker determines product saved status. Incomplete original requests retain their ID/recovery responsibility as pending_reconciliation, without subset success. Pure placement produces neither source RevisionIds nor whole-tree byte proof. Release protection, then update indexes and publish immutable manifests asynchronously. Index or synchronization failure does not undo saved status.
6. Resolve a lost response through `operationStatus` on the original ID. Missing responses never trigger another create, UUID allocation, charge or external effect. Synchronization independently reports pending/published/conflict; upload success is not save success.

These steps provide atomic multi-object visibility for Core readers and recovery responsibility, not instantaneous multi-file atomicity for ordinary external tools. Controlled Server paths or qualified backends can preserve plan conditions throughout installation. An open directory must reject unproved guarantees for unprotected namespace conditions.

Recovery reads the durable operation first, then actual files. Without its commit marker, an after hash cannot manufacture saved status. Each planned object is `before`, `after`, `third_state` or `unavailable`, requiring exact bytes, object and installation ownership, not byte equality alone. A continuously controlled backend proving that only the original writer changed it may resume the same plan. In an open local workspace, a crash releases handles. Uncertain partial/replacement ownership first retains actual residual bytes, then presents the original Base, recovery Draft and third state for an explicit repair/merge Plan. Never overwrite automatically, or claim an unknown external draft survived merely because before/after were retained.

An already committed r5 result remains original even when later r6 makes its old Base stale. Replay delivers the historic result; current reads read current state. Recovery cannot rewrite old Receipts/manifests from current files or resign old transactions. Revocation may pause recovery or mask delivery; it cannot turn a completed fact into an effect to execute again. Third states block only affected scopes; unrelated documents continue. Undo is a new Plan against current Base, not workspace rollback or reuse of an old commit.

## 7. Same-owner synchronization and conflicts

Managed synchronization transports one immutable `CommitManifest + exact blobs` bundle: WorkspaceId, transaction, causal parents, writer replica, all actual creations/changes/retirements, before/after RevisionIds, structure/schema changes and exact transforms. Its integrity digest covers the whole object. Invalid integrity, missing blobs, placeholders or missing parent history remain staged and do not become a head.

The default trusts the owner's devices and transport account; digests provide integrity, not protection against malicious transport. If a deployment promises untrusted-transport or revoked-device protection, use registered device identity and one commit-signature domain signing the entire manifest. Verify history at the then-valid registration/revocation causal cut. A conflicting revocation cannot disappear by choosing another branch. Two dedicated signature profiles, CP/Notice and a separate seal for every revision are unnecessary.

Synchronization transports bundles rather than writing current author files in arrival order. The receiver verifies complete identity, Workspace, causal closure and mode-specific trust, then installs through a Core Plan. It creates local observations and authorization anew; sender ReadBasis and compiler permission are not copied. Users choose a transport directory separate from the running working tree, which remains ordinary editable/backup files.

Ordinary cloud synchronization directly modifying the entire raw working tree is external editing. Preserve original files and currently committed blobs; diagnose partial state and duplicate IDs. It is not the managed causal synchronization guarantee, and provider overwrites cannot determine the winner. Users may edit the working tree directly; reliable concurrent same-owner devices should use bundle transport. Raw bytes deleted by a provider before any device saved or observed them cannot be reconstructed, and preservation cannot be promised.

A single causal successor fast-forwards according to actual dependencies. Concurrent independent-object edits can be combined by a deterministic Plan whose manifest retains all parents. Concurrent same-source, move/edit, Trash/edit, schema or constrained-range changes retain all heads and a common Base for explicit merge/choose/fork. No automatic winner by mtime, arrival, digest or filename, and no random reassignment of identity. Authorized branches of conflicted objects remain readable and Drafts survive; a resolution Plan requires fresh qualification. Unrelated objects continue.

Portable file copies never duplicate Approval-use counts, charges, provider unknowns or scheduling execution eligibility. Those live only in a continuously fenced Job execution store. Even copying an entire content workspace creates at most an ordinary content replica; it does not automatically resume external jobs.

## 8. Server authentication, disclosure and narrow fields

A trusted Server deployment selects its workspace, schema and authorization policy. The actual Server creates authenticated actor/session and current authorization generations. Client source metadata, UUIDs, types, addresses, fingerprints and historical manifests grant no hosted permission. Resources, source, fields, annotation summaries, annotation targets and history are separately authorized; deny takes precedence. Application ACLs cannot hide local files from their disk owner, and a shared writable raw directory is not Server-grade isolation.

Revocation linearizes with commit/delivery at the Server boundary. Recheck source/field reads, Query pages, cache hits, compiler output, previews, thumbnails, every download chunk and final commit. Already delivered bytes cannot be recalled; delivery stops after revocation. Protected audit retains exact actors, intents and outcomes without leaking titles, paths, counts, existence or error differences. A committed Receipt may remain undisclosed; nondisclosure does not alter the fact.

Users retain independent Drafts. After A saves r6, B's r5-based Plan conflicts and both drafts survive. Different documents are not invalidated solely by one global sequence advancing. Server failover must fence the journal and every actual file write/rename; a SQL lease alone is insufficient. The recommended single writer service holds OS file permissions; Server instances submit actions with the current fencing generation and old instances have no direct write path. Writer failover isolates the old process/volume access before enabling the next holder.

Narrow field permission obtains opaque field qualification through SOURCE's Server-internal static independence contract and protected before/after checks. It permits only specified fields. The client cannot first receive the entire source/dependency topology and then discard hidden fields. Unknown effects on hidden body/other fields or dynamic World return nondisclosing unavailable. Full-source authorization uses a separate source path. Client metadata cannot certify administrator-configured independence. Lightweight field saves need not compile hidden body for normal input.

Field-only API clients receive no complete-manifest or full-replica synchronization authority. Navigation/Query, summaries, thumbnails and Trash always obey current disclosure. Authorized Trash Query is read-only and grants no restore/write. Result handles/cursors fix audience, definition/parameters/schema, actual dependencies and completeness; they are not author permission.

## 9. Authorized compilation, Query and Jobs

`Environment` binds official compiler/syntax/stdlib, semantic-bridge build, target, frozen date, package/font locks, resource policy and hard budgets once. Library default styling follows [EDITOR](EDITOR.md) §8: its sole content authority is an authorized ordinary `.typ` module, which may have a real ResourceRef or NodeRef. Core settings select that EntityRef and enable it. Compilation transparently generates an entry importing/applying the style and including the real note. The entry has no identity; the real note remains SourceSnapshot and author ID/field authority. Environment freezes module/settings/entry-profile and actual World dependencies. Style changes mint no note RevisionId but invalidate affected preview/edit maps/semantic Query; static fields that do not consume style remain valid. Consumers reference it instead of copying carriers into every slot. Core supplies an authorized snapshot World rather than mounting host directories into the compiler. include/import/read/data/images/fonts/plugins resolve through it with complete actual positive/negative traces. Environment, font fallback, absent resources or authorization changes invalidate actual consumers.

`CompileSnapshot` retains exact SourceSnapshot, Environment, complete actual World dependencies, final official semantic projection/origin map, and output or diagnostics. Body compilation/projection failure preserves source, Draft and available static fields. Old preview is not current output. Workers have no ambient files/network/credentials/write authority and enforce terminable time/memory/output budgets. Incomplete tracing gives no strong qualification. Compilation does not create identity, save content or implicitly invoke business actions.

Type/Value, schema, Query/CEL/parameters, View/Action and export share SOURCE's semantic system while retaining original spelling and AST bytes separately. Navigation/search/filters use FEATURES Query. Partial/stale/error differ from complete empty, and index candidates are reread. Ordinary saved-query references default to current and freeze the actual revision at execution. Explicit pinned references never switch to latest; historical results never revive write qualification. Publish a complete handle only after complete evaluation. Authorized partial results may also have audience-bound read-only handles with explicit coverage, gaps and status for paged browsing; they prove no complete universe, emptiness or absence and grant no all-result mutation or strong postcondition qualification. Page size does not define the logical result. Bulk operations fix all targets and do not rerun Query at commit to expand the set.

Jobs freeze input versions, output, losses, confirmation, budget and actor; they retain steps, attempt/effect keys, approval consumption, charge settlement and stop. Applying a suggestion commits target source and annotation accepted state in one Plan. A staged conversion output is neither a saved document nor delivered download. Download fixes exact confirmed output, never changes content on resume, and authorizes each delivery. An unknown external response retains the original attempt and first queries the provider. Only proved same-key idempotency/conditional writes permit safe retry; there is no cross-network exactly-once claim. Stop blocks subsequent authorized steps without recalling completed effects.

Retention protects unresolved operations, conflict heads/Bases, exact annotation history, fixed-version references, active results/exports and necessary external-unknown blobs. Other caches can be cleared. GC cannot delete idempotency facts, tombstones or financial responsibility and thereby execute again, nor retain every projection indefinitely. Future published-contract upgrades require version recognition, original preservation, explicit staged conversion, failure recovery and actual client compatibility matrices. Undeployed earlier candidates do not require runtime decoders.

## 10. Minimal consumer interface

| Interface / objects | Owner responsibilities |
| --- | --- |
| `readEntity` / `readScope` / `validate` → `SourceSnapshot, ReadBasis, DependencySet` | Core owns authorized bytes, current objects and complete scopes. SOURCE interprets official source/values; FEATURES consumes the same Query scope; EDITOR does not rediscover files. |
| `prepare(Intent, bases)` / `commit(operationId, planHandle)` / `operationStatus` | All author actions share plans/journal/results and exact same-ID retry. SOURCE patches, FEATURES business conditions and EDITOR Draft do not create another commit entry. |
| `observeExternal` / `admitExternal` / `merge` | Capture original bytes, original-ID conflicts and incomplete state; explicitly admit/merge with new qualification. |
| `compile(SourceSnapshot, Environment)` → `CompileSnapshot` | Core owns World/authorization/worker. SOURCE and EDITOR consume the same final semantics/origin rather than another interpreter. |
| `evaluateQuery` / `readResultPage` → `QueryResult` | FEATURES defines semantics; Core binds audience/revisions/dependencies/completeness. Display, navigation and export consume one result contract. |
| `createJob` / `jobStatus` / `stopJob` / protected download | Fix inputs/responsibility/delivery. Author changes return to Plan; unknown effects are not blindly resent. |

These are minimal semantic contracts, not a claimed frozen schema for every wire field. Before implementation, freeze one strict schema generation for kind/version, required/null/unknown/duplicate handling, canonical fingerprints, typed refs and budgets. Open JSON callbacks cannot bypass typed Intent; nineteen-role adapters and multiple decoder ancestors are not inherited.
