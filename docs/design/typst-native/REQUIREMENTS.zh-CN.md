# 需求与技术方案的边界

状态：已完成本次识别范围的需求与机制分离，技术方案尚待重新选择和复核。下列清单覆盖当前目标设计及本轮明确追加的需求，不声称已逐字审计全部历史讨论，也不表示架构重写完成。此前 Typst 修订的独立复核保留其固定范围；不能把它变成继续采用旧技术的理由。

## 1. 设计依据

按一个新项目选择技术，优先实现已确认的用户需求。沉没成本、已有代码、文档篇幅、协议名称和历史评审通过均不产生技术继承义务。用户已选择 Typst 与原生优先，这属于当前明确约束；原生语法能表达的内容优先使用官方能力，不增加另一套作者语言。

一项设计条款须分清：用户要完成什么；结果必须满足什么可靠性、隐私或体验条件；当前建议怎样实现。前两者形成可观察的验收，后者可以重新选择。需求不能靠删去失败场景来简化；技术也不能靠重命名保留全部旧复杂度。

## 2. 分类示例

| 用户结果或验收条件 | 可替换的技术手段 |
| --- | --- |
| 改名、移动后稳定 ID 链接仍指向原笔记；路径链接失效时明确提示、不误指；复制得到独立笔记 | 具体 ID 编码、定位数据结构、分配阶段和回执字段 |
| 同级独立标题和接正文标题混用，共同编号、目录和引用 | 原生 show 规则的组织、编辑器适配结构、默认间距实现 |
| 简单联系人、组织、任务和论文属性可编辑和查询 | schema 内部编号、索引结构、投影协议；不恢复复杂事实模型 |
| 保存、崩溃恢复和重试不丢稿、不重复执行已完成操作 | 事务日志格式、提交阶段、CAS 的组织及具体证明对象 |
| 撤权后不能借缓存、搜索、编译或导出读取隐藏内容 | 权限版本、依赖追踪和缓存失效算法 |
| 本地使用、同步和服务端多用户非实时编辑具有明确的冲突与权限行为；实时协作保持原后置边界 | 副本协议、持久版本编码、传输对象及服务部署结构 |

表格用于区分结果与机制，不代替完整功能清单。已批准的功能、仅讨论的建议、调研候选和暂缓事项必须分别记录；出现于旧文档或竞品调研并不自动成为必须实现的需求。具体算法若由当前需求论证成立，可以继续采用，但理由必须是适用性与验证结果。

## 3. 历史与兼容

历史输入、原评审和实验结果保持可追溯；它们是设计证据，不是新系统运行时依赖。旧候选中的 CP、Notice、Proof、Policy、回执及 decoder 版本不得仅因已写入文档而强制进入新实现。此前的“保持原协议形状”“保持原错误顺序”等条款进入技术重审，不自动视为新项目约束。

只有存在明确的真实数据、已部署接口或用户确认的兼容对象，才据此定义兼容需求。目前仓库原型和未实施设计本身不能证明这些对象存在。发现真实数据时保留原件，另行确定显式导入、转换或兼容范围；不得删除用户数据，也不得为未部署候选虚构迁移层。

原 21 项及后续发现先还原为完整失败场景和用户损害。问题仍适用则新方案必须解决，可以使用新的办法；旧机制被取消而使场景不再适用时，记录依据。既不机械继承旧修法，也不把所有旧 CLOSED 复制为新方案通过。

## 4. 后续交付

以第 5 节的需求清单和第 6 节的失败场景为输入，给出能够满足它们的简洁技术方案。说明必要的复杂性、关键取舍和需要原型验证的风险，并逐项连接需求、方案与证据。独立复核分别检查需求是否遗漏、机制是否充分和是否存在无实际用途的历史兼容。

标题、副标题、同级混排、Word 输出以及论文数据的补充继续属于本次工作。它们不能只补进旧协议就视为完成；应与重新选择的架构一致。当前技术条款仍作为可检查的候选保存，具体替换完成前不混用两套协议。需求与技术复核完成后再进入新的全局终审，产品实现与验收另行记录。

## 5. 需求清单与范围

## 6. 原 21 项如何进入新设计

原 ID 前缀为 `A2-GLOBAL-6B13-`，原固定范围的报告和 CLOSED 保持历史事实。以下只提取需求和失败后果，**全部仍需新方案验证**；不声明新关闭。原机制消失可以使原字段级反例不适用，不能使通用损害自动消失。后续 Typst 发现也按同样标准处理。
