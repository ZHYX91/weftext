# Testing and release evidence

Status: current architecture contract.

## Evidence layers

Quality claims are separated into:

- Core source tests;
- real-filesystem integration tests;
- CLI tests;
- packaged Desktop tests;
- supported-browser WebUI tests;
- packaged Server/container deployment tests;
- multi-client collaboration tests;
- backup and disaster-recovery drills;
- manual daily-use and accessibility acceptance.

Passing one layer does not substitute for another. A build or unit test cannot establish GUI usability, browser compatibility, deployment security, collaboration convergence, or recoverability.

## Core and storage matrix

Target-format tests cover the required marker, same-named AsciiDoc root/child nodes, the sole top-level `weftext` mapping, every shallow envelope field including root-only `template_library_root`, invalid/duplicate identity, role-based reserved naming, rule-classified loose files/directories/resources, unmanaged subtree barriers, ignored content, missing documents, rename/move identity preservation, copy rekeying, parent derivation, ordering, resources including node-owned `.md` files, `weftext.annotations.json`, role-constrained `weftext.template.json`, the closed `.weftext-trash/_weftext.items` class, the closed task-node header profile, Chrono paths, and index rebuild. Content-rule tests retain ordered matching, glob/escape/case/path safety, canonical-document conflicts, the distinction between a byte-preserved node-owned Markdown attachment and explicitly classified ownerless unmanaged Markdown, ignored non-disclosure, reserved Trash-store non-classifiability, and symlink plus Windows junction/reparse fail-closed behavior. Resource-import tests accept `.md` while still rejecting canonical documents, reserved sidecars/stores, unsafe names, stale revisions, and overwrite. Direct-child Trash entries, trailing `task:[...]` occurrences, and the retired Query grammar remain private conversion tests rather than managed-runtime positive fixtures.

Link tests cover explicit-link source order, canonical names, `weftext.aliases`, exact and normalized matching, Unicode text, longest-match-first ordering, contained overlaps, ambiguous aliases, duplicate mentions, stale revisions, excluded source regions, index rebuild, and preview/commit behavior. For `ABC` and an overlapping `AB` candidate at the same occurrence, `ABC` is the primary candidate and linking it removes that occurrence of `AB` from the current candidate set.

Path and filesystem tests cover Windows, macOS, and Linux rules as platforms become supported: Unicode normalization, case-only rename, reserved names, long paths, file locks, symlinks/reparse points, placeholders, network mounts, and external moves.

## Data-safety faults

Fault injection covers temporary-file creation, partial write, flush failure, atomic replace, multi-file prepare/commit/cleanup, disk full, process termination, stale revision, external modification, transaction recovery, Trash restore, conflict keep-both, and backup restore. Device-local draft tests cover restart persistence, verified replacement, interrupted staging that retains the last good draft, corrupt-record visibility, stale external revisions, explicit discard, cleanup after commit, and Safe Mode draft persistence without workspace mutation. Tests assert that every target is either the complete old revision or complete new revision and that ambiguous evidence is retained rather than cleaned silently.

The Trash acceptance matrix is release-blocking on every claimed caller. Core/real-filesystem cases cover:

- exact and case-fold same-name node/resource conflicts without overwrite, repeated delete/restore/replay, and item-ID occupancy/collision;
- one item for a deleted subtree, unchanged descendant names/UUIDs/annotations/resources, and separate resource items sharing one batch `operationId`;
- A still inside B when B is deleted, A deleted before B, B restored before A, and an explicit atomic parent-chain restore;
- active, trashed, missing, and `originStatus: unknown` parents/owners, with no name-based parent fabrication and explicit target/rename requirements;
- external manifest/payload modification, directory/manifest ID mismatch, duplicate permanent UUIDs, extra/missing payload entries, non-UTF-8/link/reparse paths, and exact/case-fold sync conflict copies;
- stale revision, every prepare/apply/publish/verify crash boundary, all-or-nothing resource batches, idempotent recovery, and preservation of ambiguous evidence;
- refusal of unmanaged/ignored boundary subtrees and raw unmanaged, ignored, canonical-document, sidecar, transaction, or reserved-store resource deletion;
- conversion direct-layout inventory, origin-unknown conversion, collision/blocking behavior, migration recovery/rollback, and refusal to retain two runtime authorities;
- resource original/alternate-owner restore, explicit rename, no-overwrite, byte/digest equality, and node/resource item backup round-trip; and
- a distinct higher-permission permanent-delete preview/confirmation/commit path that cannot address active nodes, malformed items, or unreviewed bytes.

Workspace-revision tests change one manifest byte, payload byte, empty payload directory, and item pathname independently and require a new revision. Synchronization tests prove a partial/duplicate/conflicted item never appears as a valid active node or restorable item and is never hidden as unmanaged/ignored. Full-backup and clean-drill tests prove every item-store byte and empty directory is present and its manifest relation verifies after restore.

## UI and accessibility

Draft, Safe Mode, exact UTF-8 edit, CJK/RTL/IME, large-document, navigation, and stale-revision cases remain cross-surface. Live profile cases prove the browser receives canonical Core AsciiDoc ranges/plans without owning a second parser or Template compiler. Source cases cover fail-open invalid `weftext` envelopes, default folding with an explicit toggle, selection-driven unfolding, and exact splices preserving unrelated line endings. Write/Read conceal operational YAML; Properties exposes document-header attributes separately from node controls; Source reveals exact bytes. Annotation tests include overlapping marks, concurrent threads, actor state, orphaning/reanchoring, suggestions, promotion reanchoring/blocking, Template design-annotation omission, Server serialization/non-disclosure, and crash-safe sidecar transactions.

Desktop, CLI, Server API, and WebUI consume the same checked-in mixed-content fixture and assert identical classes, relative/parent locators, optional UUID/owner fields, no canonical-document duplication, derived icons, and ignored-content non-disclosure. Structural and resource tests prove Core cannot enter, overwrite, or move a classified boundary. Search and index tests prove unmanaged and ignored Markdown never become node-search or link evidence. Shared-navigation cases run against both Desktop and Server WebUI projections. They verify that Explorer Hierarchy contains managed nodes only; Contents shows exactly the immediate Core-visible children; canonical node AsciiDoc is not duplicated; ignored/unauthorized content affects no rows, counts, breadcrumbs, search, recents, events, or accessible names; unmanaged directories browse without fabricating tabs; and unmanaged files/resources expose no node-only actions. The existing ordering, focus, keyboard, screen-reader, zoom, high-contrast, RTL, long-name, narrow-width, and 10,001-node performance cases remain required.

The node-action semantics matrix is release-blocking across Core, Desktop, local/hosted WebUI, CLI, and Server DTOs. It proves:

- with the second pane focused, create-under-current, rename/move/copy/Trash, and current-node Chrono all capture that pane's UUID rather than the primary pane's selection;
- a context action opened from an explicit Hierarchy, Contents, search, Chrono, Trash, or resource row remains bound to the captured UUID/item ID when pane focus, selection, navigation, refresh, virtualization, or row order changes before preview or commit;
- rename, move, copy, branch-to-Trash, item restore, owned-resource-to-Trash, and permanent item deletion are separate registry entries and dialogs with only relevant fields; rename is not move-with-name, Trash has no destination controls, and permanent delete has distinct styling, authorization, and second confirmation;
- every preview carries byte-exact Core-derived `scopeSummary` values for root, descendants, resources, annotation sidecars, bytes, affected/rewritten documents, identity policy, item count, and operation ID, and every caller transports the same closed fields without frontend recounting;
- rename/move/Trash/restore preserve permanent UUIDs, copy rekeys every copied node and exposes the complete mapping, and the entry plus confirmation communicate that difference before commit;
- a dirty source root, dirty descendant, dirty resource owner or preserved Trash identity, and dirty document hit by an exact document/link rewrite each block before an executable preview; saving or explicit discard followed by repreview succeeds, while an unrelated dirty node remains unblocked;
- a required node becoming dirty after preview is caught again at commit with no write, and copy can never copy the invisible older disk version behind a dirty source draft;
- one branch with multiple descendants produces, counts, and renders one `trashItemId`, while a resource batch renders one item per independently restorable file with one shared `operationId`;
- resource deletion accepts only the Core-proven node-owned regular file and cannot reinterpret unmanaged/ignored content, canonical documents, annotation sidecars, reserved store bytes, links, or reparse points as a resource; and
- accessible names and descriptions define a node branch as its same-named document, descendants, owned resources, and annotation sidecars; destination exclusion explicitly says the complete branch is still operated on, and raw action IDs are absent from the rendered accessible UI.

The matrix includes preview/commit race and stale-revision cases on real filesystems, shared bridge/API serialization fixtures, keyboard-only and screen-reader assertions, and packaged Desktop/browser workflows. A frontend unit test or help card cannot close the action-target, draft-gate, scope-evidence, or transaction requirements.

Explorer acceptance requires Core projection, caller parity, React interaction, Server thin-client, and 10,001-row windowing tests. Real Windows Desktop and real loopback Server WebUI checks cover disclosure versus open, unmanaged browsing without editor replacement, split-pane following, keyboard focus movement, stable natural content order, long/mixed-direction text, narrow Explorer layout, and an explicit high-contrast theme. Those checks are interaction evidence only: a physical screen reader, full IME composition session, browser zoom matrix, and operating-system reduced-motion session remain manual acceptance work and must not be inferred from automated semantics or CSS coverage.

Packaged Desktop acceptance requires automated cases for structured Write exact-source/frontmatter continuity, Core-provided semantic decorations, mixed-line-ending table edits restricted to a Core table range, per-workspace UUID-only tab/history/bookmark/recent/split restoration, duplicate-tab avoidance, portable-icon revision validation, and external search-index rebuild/delta/delete/Trash behavior. Backend failure injection must show that a document or structural commit remains reported as successful when its post-commit derived-index refresh fails, with a structured warning that does not invite a duplicate write. Path tests cover lexical `..`, relative paths, not-yet-created targets, symlinks, and Windows junction/reparse aliases where supported. Live Desktop tests restore the active tab's UUID rather than only demo localStorage, reject stale second-pane recovery drafts from automatic display, and exercise an explicit revision-checked second-pane preview/commit/conflict path. These are engineering gates, not evidence that a physical IME, screen reader, keyboard, display mode, or packaged lifecycle has been manually accepted.

Canonical-profile UI cases prove native h1–h6 output, accessible H7–H9 roles without invalid elements, actual outline levels, compact H1–H9 conversion, and exact AsciiDoc source continuity. Quote cases cover exact depths 1–9 and greater than nine, protected markers, Core text/source ranges, increase/decrease operations, and consistent nested Write/Read/Source presentation.

## Performance

Benchmarks include 10,000 and 50,000 nodes, 100,000 or more links, resource-heavy subtrees, large canonical AsciiDoc documents, annotation-heavy documents, many simultaneous sessions, and cloud-synchronized local workspaces. Structural changes propagate deltas: an ordinary rename or move must not reparse unchanged descendants or rebuild unrelated indexes.

Performance budgets are recorded before optimization and become release gates only after representative hardware and datasets are published.

The current sizing benchmark creates 10,000 child node directories plus the root on a real temporary filesystem, rebuilds the external index, and finds the last representative body token. It asserts 10,001 indexed entries and one exact result; elapsed rebuild/query time and index bytes are emitted for evidence but are not yet a normative budget. A separate delta case asserts zero reparses for an unchanged three-node workspace and exactly one reparse for an explicit one-node invalidation or ordinary changed document.
