# Workspace transactions and Trash

This specification defines the workspace transaction boundary. Structural actions, Trash, Query, Template Library, multidimensional table, document merge/history restore, and backup-repository actions may be exposed only through the revision-bound, recoverable contracts below.

## Workspace revision

A structural action is planned against a workspace revision derived from Core-classified portable authority. Core hashes the required `.weftext-format`, `.weftext-rules` when present, managed node directories/AsciiDoc documents, visible unmanaged directories/files, resources, annotation sidecars, every valid table sidecar/shard/record byte, and every directory/manifest/payload byte in `.weftext-trash/_weftext.items`, using `/`-separated UTF-8 relative paths sorted by path and kind. Ignored entries do not participate in ordinary structural revisions because those transactions cannot read or mutate them; the dedicated full-backup inventory still includes them. Table-record and Trash-item authority always participates in the workspace revision even though product discovery does not expose either as ordinary files and content rules cannot classify inside their stores. Changing a rule or the format marker always changes the revision. Derived indexes and request-owned `.__weftext-transaction-` directories do not participate.

Planning fails closed for an invalid inventory, non-UTF-8 path, symlink or reparse point, unreadable entry, duplicate identity, or another unfinished transaction. Commit recomputes the same revision immediately before mutation. A mismatch is a stale workspace conflict and never authorizes replanning or overwrite.

Planning also fails when a destination is classified unmanaged/ignored, a managed file action would create a classified path, or a move/copy/Trash/restore source subtree contains an unmanaged or ignored boundary. This deliberately avoids moving hidden or non-node bytes as an accidental side effect of a node operation. A valid table sidecar/record store inside the selected managed branch is typed branch authority rather than an accidental boundary and must be planned completely; an invalid/partial table relation blocks the structural action. A destination inside an unmanaged subtree cannot be named by node UUID because Core never indexes one there. Resource imports, table-resource references, and annotation-sidecar creation validate their exact file targets against the same rule set.

## Deterministic plans

The transaction contract requires revision-bound previews for the following actions:

- create a child node;
- rename a node subtree without changing its parent;
- move a node subtree without hiding rename inside the move action;
- copy a subtree while assigning a fresh UUIDv4 to every copied node;
- move one complete managed subtree into a newly generated Workspace Trash item;
- move one or several independent node-owned resources into separate Trash items sharing one operation ID;
- restore a Trash item to its proven origin, restore an exact parent-item chain atomically, or restore to an explicitly selected active target/name;
- permanently delete selected Trash items under a distinct high-permission confirmation;
- migrate a direct-child Trash layout into closed origin-known/unknown items; and
- rewrite explicit internal-link occurrences whose resolved target locator changes; and
- patch the portable adjacent-heading/body presentation setting without reserializing frontmatter;
- promote one exact native checklist occurrence into a newly generated managed task node while replacing the source branch by a stable `node:` link; and
- replace a task node's complete dependency set only after validating the proposed authorized full graph; and
- internally execute one complete local trailing-task-macro migration through the sealed `TaskMigration` authority described below; this is not a caller-visible action.

A future Template transaction package must add distinct revision-bound previews to configure/rebind/clear the root's exact Template Library UUID, instantiate one reviewed Template Root as a complete fresh-UUID ordinary subtree, and move/restore a branch across Template roles through explicit source/sidecar conversion. These are not currently exposed `Core` actions and cannot be synthesized from ordinary move/copy/Trash DTOs.

A future multidimensional-table transaction package must add distinct revision-bound previews to create a complete table node; add/edit/bulk-edit records; soft-delete/restore/permanently-delete table-local records; add/rename/remove/convert fields and options; add/edit/remove shared views; import or repair referenced resources; update typed relations; copy/rekey a complete table; and upgrade one exact native AsciiDoc table range into a fresh table node plus canonical block embed. These are not ordinary document/resource actions and cannot be synthesized by a frontend from raw paths or generic JSON writes.

A caller resolves an action target once before planning. A current-node/editor command supplies the UUID captured from the focused pane; a row command supplies the explicit UUID or Trash item ID captured from that row. Core accepts only this immutable typed identity and records it in the plan. Neither planning nor commit reads a client `selectedNodeId`, followed-node value, visual row index, focused pane, or raw display path. A focus/selection change after invocation has no effect; an unavailable or stale identity fails instead of being resolved again.

A plan records the action, semantic action ID, plan ID, base workspace revision, captured target identity and origin, acting node IDs, old and new workspace-relative paths, generated copy IDs, and exact document replacements. UUID generation happens once during planning and the previewed values are the values committed. Preview evidence is canonically ordered; executable steps retain their deterministic dependency order.

Every rename, move, copy, node-to-Trash, and node-restore plan carries one closed, versioned Core-authored `scopeSummary` with: `rootNode: { nodeId, displayName }`; `descendantNodeCount` excluding that root; `resourceCount`; `annotationSidecarCount`; exact `byteTotal`; canonically ordered `affectedDocumentNodeIds` and `rewrittenDocumentNodeIds`; `identityPolicy` (`preserve` or `rekey`); `trashItemCount`; and nullable `operationId`. For an atomic ancestor-chain restore, `rootNode` is the outermost restored node and the captured target separately remains the user-selected item. `affectedDocumentNodeIds` contains every document whose active/payload locator or bytes differ between the bound pre-state and proposed post-state: preserved source IDs for rename/move/Trash, generated destination IDs for copy, restored IDs for restore, plus any separately rewritten document. `rewrittenDocumentNodeIds` is the subset receiving exact source replacement. `byteTotal` sums each unique regular file whose current bytes are relocated, copied, itemized, restored, or replaced once; directories contribute zero and an overlap is never double counted. Counts and bytes are derived from the same validated physical inventory and document replacements that drive the journal, not from a client tree or post-hoc estimate. Non-Trash plans report zero items and a null operation ID; an item-producing Trash plan reports its generated operation ID. Rename, move, Trash, and restore use `preserve`; copy uses `rekey`, carries the complete old-to-new UUID mapping, and never copies a source node from older disk bytes while its visible draft is dirty. One trashed root branch reports one Trash item regardless of descendant count. Create/import and resource-only or heterogeneous multi-item permanent-delete plans keep their dedicated typed evidence; they do not invent a preserve/rekey branch summary when no single operated node branch exists.

Checklist promotion uses dedicated closed `promotionSummary` evidence rather than pretending the new node already existed as an operated branch. It includes the captured source occurrence/range and state, generated task-node identity/title/parent/name, lifted descendant/continuation counts and bytes, initial task state, affected annotation disposition, replacement link label/source, affected document UUIDs, and exact byte total. The generated node UUID appears once as the new durable identity; the checklist has no old UUID or rekey mapping.

The plan also records Core's canonical `draftSensitiveNodeIds`: every permanent node UUID in a node source branch; every node whose canonical document is replaced or link-rewritten; and every preserved node/owner UUID contained in a Trash item or resource action whose removal, restoration, or permanent deletion could invalidate a device/session draft. Resource deletion proves both that the exact file is owned by the named node and that it is not unmanaged, ignored, canonical-document, annotation-sidecar, reserved-store, linked/reparse, or non-regular content. The versioned Core, Desktop bridge, WebUI bridge, CLI, and Server DTOs carry these fields unchanged; callers may redact display names but cannot omit identities needed for authorization or gate evaluation.

Checklist promotion additionally binds the exact owning-document revision and parser-confirmed occurrence, complete attached branch, generated node UUID/path/source, initial closed-schema task profile, exact original-position link replacement, annotation handling, and selected existing parent. `[ ]` maps to `todo`; `[x]`/`[*]` map to `completed` without a fabricated close timestamp. The default parent is the source node, but any alternate parent/name is explicit and revision-bound. A promotion journal creates the complete task node and replaces the checklist branch atomically; it never reports success with only one side present and never leaves a mirrored checkbox.

Task-node dependency planning resolves each UUID uniquely to an authorized active node carrying a valid `weftext-task` v1 profile and validates the proposed complete graph. It rejects self/duplicate/cyclic edges and does not disclose hidden versus missing targets. Inline recurrence input is handled only by explicit conversion; task-node recurrence is not part of the accepted v1 target. A change to any unrelated portable workspace byte after preview rejects commit rather than silently replanning against a different graph.

The legacy task-rebaseline inventory remains outside the executable-plan set. Its opaque complete-local-workspace filesystem capture and closed `weftext.task-rebaseline/v1` preview bind the portable workspace revision, exact source document revisions, generated identity/path proposals, annotation inventory, and an explicit `externalSnapshotBinding: not_provided`. Its `physicalInventoryBinding: workspace_revision_only` is not a complete physical pre-state, `committable` is always false, and generic commit rejects it. Decoding or revalidating this DTO never grants mutation authority.

The current sealed Core contract has separate forward and rollback authorities. Forward apply remains exclusively `workspace-transaction.v3`; Task Promotion remains the sole v2 action, and v1 journals reject both Promotion and Rebaseline. A private forward planner holds one lease across exact physical A, semantic reconstruction equal to the reviewed v1 digest and full value, external snapshot verification, and physical B = A. The external snapshot must be a complete byte-equal physical tree outside the workspace with disjoint directory and regular-file object identities. The v3 authority binds the root node UUID/document revision/filesystem identity, revision, complete A and projected C entries/digests, snapshot binding/root identity and recovery locator, full mapping, replacements/new-node bytes, annotation evidence, all active managed-document UUIDs, complete native draft observation, local Owner-boundary assertion, limits, and ordered steps. Missing, extra, duplicate, non-canonical, stale, linked/reparse, aliased, or over-limit authority fails closed.

The internal forward commit path requires a fresh local Owner assertion and fresh complete draft observation, then repeats physical A, root, semantic, snapshot, and draft checks under one lease before writing the journal. A committed-C-to-A exact rollback can be derived only from the opaque forward plan and its exact process-local committed result. Rollback planning observes complete physical and semantic C plus the unchanged disjoint exact-A snapshot, requires a current-Owner review assertion and a new complete all-active-document draft observation including generated nodes, and derives only proposed-to-original source replacements followed by generated-tree removals to holding. A legitimate new Owner or authorization epoch may review rollback; commit then requires another distinct assertion for that reviewed actor and epoch. These assertions document a trusted native calling boundary; they are not an ACL capability and are not exported. Hosted, scoped, and non-Owner callers therefore remain closed. Product execution also remains closed until real Owner/ACL authority and durable receipt/audit integration are implemented.

The canonical Query target is read-only and creates no workspace transaction. Its separate Core runtime package binds exact Query source/ranges, explicit alias/domain, typed scope, lexical embedding or Saved Query binding, explicit evaluation context, authorization, and resource limits. Landing that runtime does not claim complete product callers. Query result/action evidence never authorizes a later mutation without the ordinary target-specific revision-bound plan.

Multidimensional-table record/schema actions are not canonical Query mutations. Each plan binds the table-node UUID, record UUIDs, exact sidecar/record/resource fingerprints, proposed closed JSON bytes, schema/type validation, relation targets, active/trashed state, draft-sensitive node IDs, authorized actor, byte/count totals, and every journal step. A schema conversion stages and validates the prospective sidecar plus every affected record before commit. Move preserves table and record identities; copy generates the complete fresh node/record mapping and rewrites internal record relations; whole-node Trash/restore preserves the exact store. Soft-deleted records stay in their exact table files, while permanent record deletion requires distinct high-permission digest confirmation and never guesses resource ownership.

Document comparison and Version History browsing are read-only and create no workspace transaction. Applying selected comparison dispositions or restoring one historical document source requires a future `DocumentMergePlan` or `DocumentRestorePlan` governed by specification 22. The plan binds the current target node/document/workspace revision, every immutable compare/history/backup input digest, Core-authored hunk dispositions, exact proposed source, profile/system/protected-range validation, authorization, draft observation, expiry, and recovery steps. Same-node restore preserves current `weftext.id`; different-node comparison never authorizes identity copying. Stale inputs or target authority reject rather than rerunning a diff against new bytes.

Recent History capture is post-commit secondary evidence. A successful workspace mutation is not rolled back or reported failed because its device-local history entry could not publish; the commit response instead carries `history_capture_failed`, and callers never retry the workspace write. Formal Backup Repository snapshot/protection/retention/garbage-collection actions use a separate repository transaction/lease because their target is disjoint from the workspace. A repository snapshot binds one exact workspace physical inventory/revision but writes only immutable external objects and a manifest last. Restore into the active workspace returns to the normal workspace preview/draft/no-overwrite/journal boundary; repository bytes or a raw snapshot path never grant mutation authority.

The future Template Library configuration plan must bind the root revision, reviewed Template Library node UUID, unique active resolution, role consequences, and all diagnostics. It never infers a target from name/path or treats direct sidecar creation as role authority.

Future Template instantiation must use dedicated closed `templateInstantiationSummary` evidence rather than pretending to copy an ordinary node branch. It freezes the Template Root and every Part UUID/document/sidecar revision, parameter schema plus typed input/context, each evaluated binding and applied/default disposition, target parent, resolved single-authority target name, name source, fresh generated UUID/path mapping, exact proposed sources, internal and external link dispositions, resource bytes/digests, omitted design-annotation counts/bytes, source and destination ACL, collision diagnostics, draft-sensitive IDs, byte/count totals, and every journal step. A Root `node_name` binding supplies the destination name with no caller override; without it the caller supplies the explicit name. A Part binding supplies its name, otherwise its prototype basename does. All generated nodes are ordinary; success contains no Template role, `weftext.template.json`, or residual slot/profile source.

A future Template role-boundary move must freeze both the ordinary structural scope and a `templateRoleTransitionSummary`: old/new Library/Root/Part role and owning Root, exact sidecar creation/removal, every source transformation needed to activate, materialize, or delete slots, residual/protected diagnostics, links/resources/annotations, target occupancy, ACL, and drafts. Moving into direct-child position requires one valid proposed Root sidecar; moving into a Part position forbids nested sidecar authority; moving out proves no formerly active Template slot/profile/sidecar survives in ordinary output. Independently written ordinary slot-like source stays inert, but no path-only plan or external-sync application may silently downgrade a validated prototype; it blocks as repair-required instead.

When a copied document links uniquely to another node inside the copied subtree, the copy plan retargets that locator to the copied node. External links remain pointed at their original targets. Ambiguous occurrences are not guessed.

The workspace root cannot be moved, copied inside itself, trashed, or restored. A node cannot move into its own subtree. Existing destinations, case-fold collisions, invalid portable names, reserved transaction/rule/Trash-item paths, content-boundary crossings, and ambiguous link targets reject planning. A raw path is never sufficient authority for Trash restore or permanent deletion.

### Exact device-draft gate

The shared native/Server mutation boundary supplies Core with an authoritative draft-registry view for the invoking device/session. `previewWorkspaceAction` intersects that registry only with `draftSensitiveNodeIds` and returns scoped evidence: the required-clean UUIDs, exact blocking dirty UUIDs, and an opaque draft-store observation bound to those UUIDs. When the future Template package lands, instantiation must include every Template Root/Part source node so it cannot instantiate older disk bytes behind a design draft; a role transition must include every node whose role/source/sidecar or ownership changes, plus every separately rewritten document. When the intersection is non-empty, Core may return the scope for explanation but does not issue an executable commit token. The user must revision-save or explicitly discard every listed draft and request a new preview. There is no “use disk version anyway,” global “ignore drafts,” or action-specific bypass.

Immediately before journal application, `commitWorkspaceAction` repeats the authoritative lookup for the plan's exact `draftSensitiveNodeIds` and rejects any newly dirty member without writing. Both entry points implement the gate; a caller-only warning is insufficient. Commit also performs the ordinary workspace/document revision checks, so saving an affected draft after preview makes that preview stale and requires replanning. A dirty node outside the exact source/replacement/rewrite/Trash identity set neither blocks preview nor invalidates commit merely because it is dirty. UI state, a cached client boolean, and a globally changing unrelated-draft counter are not gate authority.

## Recoverable journal

An executing plan owns one root-level directory named `.__weftext-transaction-workspace-<plan-id>`. It is temporary recovery evidence, not portable content or index authority, and semantic scanners ignore it. The directory contains a versioned `journal.json`, verified staged content, and any originals needed for rollback. A v3 physical post-state/recovery scan may exclude only the exact currently validated journal directory object and the held lease anchor; it must not ignore arbitrary transaction-shaped names.

The durable states are:

1. `prepared`: the base revision is verified and all replacement/copy bytes are staged and digested; no portable target has changed;
2. `applying`: the journal is durable; verified old/new/staged/holding digests allow recovery to infer the last completed step without guessing;
3. `committed`: the expected final inventory and revisions have been reopened and verified; cleanup may resume safely.

For v1/v2, startup recovery removes an intact `prepared` journal, rolls an `applying` journal back in reverse step order, and verifies then removes a `committed` journal. V3 instead classifies the complete journal-excluded workspace tree against bound pre=A and post=C plus the closed per-step states: `prepared` accepts only A; `applying` cleans exact A, rolls a closed mixture back to exact A, or semantically verifies and finalizes exact C; `committed` accepts only verified C. The independent `workspace-transaction.v4` is reserved for `TaskRebaseline` exact rollback and requires the explicit `rollback_rebaseline` direction. It classifies pre=C and post=A: `prepared` accepts only C; `applying` cleans exact C, reverses only the closed ReplaceFile/RemovePath mixtures to exact C, or semantically verifies and finalizes exact A; `committed` accepts only verified A. ReplaceFile covers the destination/staged/displaced states on both sides of its two renames, and RemovePath covers only exact generated source versus exact holding. Before accepting even an exact physical pre/post tree, v3/v4 validate the complete expected staged/displaced/holding matrix and reject unknown transaction artifacts. Every classification also revalidates the external snapshot as exact A and checks root filesystem identity. Recovery never guesses when any untouched, ignored, unmanaged, annotation, Trash, or other byte differs. It retains journal/staging/snapshot evidence, marks recovery required, and overwrites nothing unknown. Recovery safely closes durable evidence without rechecking current ACL; initiating a new rollback still requires current Owner authority.

Journal workspace paths are relative and validated on every read. Absolute paths, `..`, symlinks, unknown schema versions, duplicate steps, and paths outside the selected root fail closed. V3 and v4 each carry one canonical UTF-8 absolute external-snapshot locator inside private recovery authority; it is bounded before staging, bound into the journal digest, revalidated as disjoint exact A, and redacted from public DTOs and `Debug`. V3 has no durable direction field and remains permanently forward A-to-C; v4 has a mandatory rollback direction, so schema/action/direction confusion fails closed without changing existing v3 bytes. Future Template journals must additionally validate every generated UUID/path/source, copied resource, rewritten link, sidecar disposition, and role transition against the closed summary. Journal cleanup cannot make generated source, resources, identities, Template roles/sidecars, or Trash state authoritative.

## Workspace Trash

Workspace Trash is the reserved hidden root child `.weftext-trash`, with the same-named `.weftext-trash.adoc` canonical document and persistent node UUID. It may be created on first use through the same transaction journal. Users cannot create, rename, move, copy, or resource-edit an ordinary item at a reserved Trash path. Deleted objects live only under `.weftext-trash/_weftext.items/<trashItemId>`; `_weftext.items` is a special Core storage domain rather than a managed child, resource, unmanaged directory, ignored directory, derived index, or transaction journal.

### Trash plan authority

A generic node-to-Trash plan must refuse the UUID currently named by root `template_library_root`. The future Template transaction package may trash that container only in one combined plan that clears the field or rebinds it to another uniquely valid active node and previews every resulting role change. Neither a path move nor Trash publication edits configuration implicitly.

A Trash plan records the complete base workspace revision; a generated lowercase UUIDv4 `operationId`; one generated, exact/case-fold-unoccupied lowercase UUIDv4 `trashItemId` per independently restorable object; the exact source identity/path and physical inventory; closed manifest bytes and digest; exact payload inventory, lengths, and digests; required first-use directories; and an ordered journal program. The item directory and manifest ID must match. UUID generation happens once during planning and commit never regenerates or silently suffixes one.

One deleted node root produces one `kind: node` item containing the complete unchanged same-named directory and all descendants. The manifest binds its permanent node UUID, original parent UUID/name, optional ancestor UUID hints, and complete payload-tree digest; descendants do not become items. One deleted resource file produces one `kind: resource` item binding its original owner UUID/name, exact length, and SHA-256. A batch creates separate resource items with one shared `operationId` and commits all-or-nothing. A managed subtree with an unmanaged/ignored boundary and a file that is unmanaged, ignored, reserved, linked/reparse, non-regular, or not owned by the named node fail before a plan exists.

Commit rechecks the complete workspace revision, source evidence, every item-ID occupancy, manifest/payload shape, and destination boundary. It creates request-owned no-clobber staging, flushes and reopens every byte, durably enters `applying`, moves sources into staged payloads, publishes each complete item directory without replacement, and verifies the expected revision. Failure injection at any step recovers the exact old state; a reported success contains every item and no source, while a reported rollback contains every source and no item. Unknown mixtures retain the journal and all evidence.

If A remains inside B when B is trashed, B is one item. If A is trashed first and B later, there are two items and A's manifest relates to B only by B's permanent node UUID. A common name or historical path does not create that relationship.

### Restore and permanent deletion

Restore planning starts from a complete validated item manifest/payload, not a path. An original-position plan exists only when the recorded parent/owner UUID is active and the exact plus platform case-fold target is free. When the missing origin resolves uniquely to one or more complete node items, Core may construct an explicitly reviewed atomic `with-ancestors` plan that restores the outer parent chain before the selected node/resource. It never extracts a nested descendant as though it had an independent manifest.

If the origin is genuinely missing or the migrated manifest has `originStatus: unknown`, Core leaves the item in Trash until the user selects an existing active parent/owner UUID. A name conflict requires an explicit portable rename or different target. Core never creates B1 from a stored name/path, never overwrites exact or case-only conflicts, and never treats ancestor hints as authority. Restore preserves permanent node UUIDs, revalidates installed bytes, consumes only the restored item directories, and is replay-safe. A Trash payload containing former Template source is closed inactive exact-byte evidence, not an active ordinary subtree. Restore to its proven Root/Part position under the still-configured Library may retain exact bytes. Any restore to ordinary space must use the future role-conversion plan to materialize/delete active slots and remove profile/sidecar or block. Restore never guesses or rebinds `template_library_root`; only an exact rollback receipt for the combined configuration/Trash transaction or a separately reviewed configuration plan may do so.

Permanent deletion is a separate plan that binds selected item IDs, exact manifests, payload digests, byte totals, base revision, higher permission, and explicit confirmation. It cannot address active nodes/raw paths or clean malformed/conflicted items. Retention policy can propose this action but cannot bypass the same journal and authorization. Trash is not backup.

### Inventory, sync conflict, and migration

Core inventories Trash items as a closed special class. Active node discovery, links, search, Chrono, tasks, and queries do not enter payloads, but retained permanent UUIDs must remain unique across active and trashed authority. Missing/extra manifest or payload entries, ID mismatch, duplicate/case-fold item IDs, active/trashed duplicate UUIDs, changed aggregate digests, sync conflict copies, partial arrival, and simultaneous restore/delete evidence produce typed reconciliation states. No ordinary mutation proceeds through one.

The direct historical layout `.weftext-trash/<name>` is migration input only. A read-only migration plan inventories and digests every legacy entry, generates item/operation IDs, blocks collisions/unsafe bytes, and creates one closed v1 item per independently recoverable entry. Without cryptographically or transactionally bound origin evidence, the manifest uses `originStatus: unknown`, a null original parent/owner UUID, and requires explicit-target restore. Migration is externally snapshotted, revision-bound, journaled, recoverable, and rollback-verifiable; Core never keeps direct entries and `_weftext.items` as dual runtime authorities.

The complete layout and closed manifest contract are in [`../architecture/17-workspace-trash-item-store.md`](../architecture/17-workspace-trash-item-store.md). Synchronization carries item bytes as portable authority, but unfinished transaction journals remain local recovery evidence and are never collaboration coordination.

## Caller boundary

Desktop, WebUI, Server, CLI, and approved Agent mutations call the same plan, commit, and recovery functions. UI code cannot move files, assign Template roles, evaluate slots, mint generated UUIDs, copy resources, or rewrite links directly. Canonical Query callers consume the same read-only Core plan/evaluator and cannot turn a result row into mutation authority without a new typed action plan. DSH remains read-only until its proposal and approval envelopes can bind the exact plan ID and base workspace revision to this commit path.
